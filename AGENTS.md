# intoDeDung — правила Codex

## Работа ведущего
Ведущий — архитектор и интегратор. На содержательных задачах разработки
используй субагентов по правилам ниже, когда есть ограниченная делегируемая работа.
Это постоянное указание делегировать; повторное разрешение на каждого помощника не нужно.
Вопросы, мелкие правки и настройку процесса решай локально, если делегирование дороже.
Не создавай самостоятельные задачи в боковой панели без прямого запроса пользователя.
Не запускай работу по расписанию: этот процесс действует во время назначенной задачи.

## Старт и контекст
Ведущий сначала читает docs/CODEX_HANDOFF.md. Проверяет git status и текущий commit.
Затем адресно читает нужные разделы ARCHITECTURE, DECISIONS, TESTING и код.
Если передача устарела, сверяет код и обновляет её; не принимает старую сводку за факт.
Исполнителям передавай самодостаточный пакет вместо истории чата:
цель, base commit, разрешённые файлы, необходимые API, критерии и команды проверки.
Шаблон и процесс — docs/CODEX_WORKFLOW.md. Не загружай всю библиотеку документов кодеру.

## Роли и модели
- game_scout: gpt-5.6-luna / low — адресный поиск, только чтение.
- game_coder: gpt-5.6-luna / medium — небольшая реализация по точному ТЗ.
- game_reviewer: gpt-5.6-terra / high — независимое ревью, только чтение.
- Архитектура и критическая интеграция: ведущий gpt-6-astra / high.
Определения ролей находятся в .codex/agents/. Если инструмент не умеет выбирать
именованную роль, прочитай соответствующий TOML и передай его инструкции,
модель и reasoning явно в поддерживаемые поля запуска субагента.
При таком fallback укажи роль в сообщении и сохрани её ограничения, не повышая права.
Если инструмент не поддерживает sandbox роли, запрет записи остаётся инструкцией,
а технические права наследуются от родителя. Не утверждай, что read-only принудительно включён.
Модель можно менять согласно этой таблице; не скрывай отказ или недоступность модели.
Используй новый минимальный контекст (fork_turns=none, если доступно).
Одновременно максимум два помощника. В общем checkout только один кодер пишет файлы.
Ревью запускай на зафиксированном результате, после завершения записи кодером.
Помощники не делегируют дальше. При делегировании продолжай полезную независимую работу.
Если независимой работы нет, выполни задачу локально или используй доступное ожидание.

## Проверка и эскалация
Сначала разбор/импорт Godot и нужные тесты, затем независимое ревью.
Перед сдачей содержательного кода требуется ревью; если субагент недоступен,
ведущий явно сообщает о замене самостоятельной проверкой.
Не вызывай ревьюера ради одного изменения текста или параметра настройки.
После двух неудачных исправлений одной причины проверь полноту ТЗ.
Локальную сложную реализацию можно передать отдельному исполнителю gpt-5.6-terra / high
с инструкциями game_coder через явный запуск, не используя read-only роль game_reviewer.
Контракты, очередь реакций, сохранения, детерминизм и preview проверяет ведущий.
Логи и полный diff не пересказывай в отчётах. Показывай итог, проверки и ограничения.
Агенты не коммитят самостоятельно; ведущий следует git-политике проекта и запросу пользователя.
Не сбрасывай чужие изменения. Не ослабляй sandbox, approvals и доверие к проекту.

## Коммиты
После завершения этапа ведущий самостоятельно фиксирует его изменения логическими
коммитами без отдельного напоминания, если пользователь не запретил коммиты.
Явное «не коммитить» в задании имеет приоритет над этим правилом.
Перед фиксацией должны пройти необходимые для изменения проверки, а для содержательного
кода — также независимое ревью по правилам выше. Для правок только текста/процесса
достаточно проверки diff; Godot и отдельный ревьюер для них не нужны.
Каждый коммит содержит одну законченную цель с её тестами и затронутой документацией;
разные этапы и независимые изменения настроек разделяй. Сообщения — Conventional Commits.
Перед staging проверь diff и включай только изменения в рамках порученной работы;
прежние или чужие изменения не включай автоматически. Не переписывай историю и не
публикуй коммиты в remote без отдельного поручения. Коммиты создаёт только ведущий.

## Правила игры и кода
Актуальное решение 2026-09-13: команды ходят поочерёдно; порядок персонажей
команды игрок выбирает сам. Инициатива не управляет ходами.
Уточнение пользователя 2026-09-14: атака стоит 1 основное действие; между своими
живыми персонажами можно переключаться произвольно, сохраняя остатки ресурсов.
Выбор не пополняет действия; действующий сценарий описан в docs/TACTICAL_BATTLE.md.
BT — выбранное направление для нового ИИ; текущий Utility AI сохраняется через адаптер.
BT выбирает намерение, команды исполняют; новые комбинации поведения не меняют ядро.
Строго типизированный GDScript. Resource = определения, RefCounted = runtime.
Позиция меняется через BattleBoard; GridDataProvider получают от доски.
core не ссылается на автозагрузки по имени; события и RNG инжектируются.
Реакции порождают команды. Preview использует реальное исполнение на изолированном
состоянии, включая влияющие предметы, RNG и ресурсы действий.
Сериализуемые enum только дополняются. Комментарии по-русски объясняют причину.
Не отмечай планируемые системы как реализованные. Сначала рабочий вертикальный срез.
