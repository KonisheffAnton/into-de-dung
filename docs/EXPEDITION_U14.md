## 1. Проверенное основание и ответственность

| Сейчас в коде | Следствие для U14 |
|---|---|

`scripts/demo/hero_hub_{battle_factory,store,screen}.gd` на base.
Контракты старого цикла — [H1](HERO_HUB_H1.md), старого линейного режима —
[D4](EXPEDITION_D4.md); новые правила не распространяются на их legacy fixtures.

`ExpeditionRunState` не хранит второй изменяемый список HP/обычной экипировки.

не alias текущего профиля. Live worker исключительно владеет session, пока
pending; UI/профиль не читают её в это время.

## 2. План похода и конечные переходы

### План и RNG

В начале выхода генерировать и сохранять весь граф и скрытый контент, включая
варианты встреч/опасностей, три предложения награды каждого нефинального боя
и seed каждого боя. Отдельные внедрённые потоки RNG для графа/наград/боёв;
найм H1 сохраняет собственное состояние. Число preview и открытий UI не меняет
ни один поток. Повтор генерации вместо загрузки запрещён.

Узел содержит stable `node_id`, слой, тип, ID/version вариантов, список следующих
ID и value-параметры комнаты/награды. План сериализуется целиком, а не только
seed: изменение каталога не должно молча поменять уже начатый поход.
Неизвестная версия контента — явный отказ восстановления без перезаписи файла.

Валидатор подтверждает весь принятый граф: размеры/слои/пулы, отсутствие циклов,
рёбра только в следующий слой, входы/достижимость финала, две развилки на каждом
пути и обязательную безопасную точку. Проверяется каждый путь, не только один.
U Q14-T1, 2026-09-30: у единственной безопасной точки ровно три выхода,
по одному во все три комнаты следующего слоя; у остальных нефинальных узлов
1–2 выхода. Принятые слои `2→3→2→1→3→2→1` сохранены. Исключение закрывает
противоречие достижимости; недостижимые или молча удалённые узлы недопустимы.

### Фазы и барьеры сохранения

Верхний профиль оставляет `hub` и legacy `battle`, добавляет `expedition`.
Внутри похода закрытый набор фаз; UI не меняет его напрямую:

| Из → в | Предусловие и единичная транзакция |
|---|---|
| `hub → route` | Непустой живой выбранный отряд; полное лечение H1 один раз; новый run ID, пустая добыча/артефакты, сохранённый план |
| `route → battle` | Выбран ровно один доступный боевой узел; зафиксировать выбранное ребро, новый battle serial и начало боя; затем открыть расстановку |
| `route → service` | Выбран привал/безопасная точка; записать вход, затем показать одноразовую услугу |
| `route → route` (тайник) | В одном commit записать посещение и золото; открыть следующие доступные комнаты |
| `service → route` (привал) | Ровно одна допустимая услуга; записать изменение ресурсов и завершение комнаты |
| `service → camp_departure` | Услуга безопасной точки применена один раз; выбор выхода ещё не сделан |
| `camp_departure → route / hub` | Явно продолжить либо вернуть весь походный результат по принятому исходу |
| `battle → reward` | Победа нефинального боя: receipt проверен, ресурсы/смерти/XP/золото комнаты учтены, сохранено ожидающее предложение артефакта |
| `reward → route` | Выбран один из сохранённых вариантов; создан ровно один экземпляр; предложение закрыто |
| `battle → hub` | Финальная победа либо поражение: награда боя (если есть) и завершение похода — один commit, без промежуточной повторной выдачи |

После `reward` на карте доступны распределение очков/артефактов и обмен обычной
экипировкой выживших согласно дизайну. Те же допустимые операции до выбора
следующей комнаты; в battle/service/reward переходы по карте закрыты.
Финал сразу завершает поход; бессмысленного распределения после переработки нет.
Возврат в меню/закрытие игры не выбирают досрочный выход.

Целевой API перехода возвращает типизированный результат (код отказа + значение),
не строку UI и не частично изменённый live-профиль. Отказ admission не меняет
ID/счётчики/RNG/ресурсы. Receipt идентифицируется `(run_id, node_id, battle_serial)`;
текущая фаза/serial исключают повтор. При успешной записи receipt уже потреблён.

## 3. Исход комнаты и сохранность ресурсов

Receipt извлекается только после общей очереди, при терминальной фазе без
FAULTED и при отсутствии pending worker. Содержит полный ожидаемый набор
исходных героев и runtime-вещей из manifest начала боя: HP, остатки брони,
победа/поражение, ID комнаты/serial. Manifest перечисляет только переданную
в бой экипировку; обычные вещи походного рюкзака не имеют runtime owner и не
должны искусственно появляться в receipt. Их записи остаются в профиле.
Проверяются полнота/уникальность/владельцы/конечность/пределы. Помощники не
подменяют исходных участников; смерть последнего постоянного героя — поражение.

На копии профиля в одном переходе: остатки ресурсов → смерти/обычные вещи →
XP победы/уровни → походное золото → снятие боевого состояния → следующая фаза.
Группы участники/резерв определяются по входному составу боя, до удаления
погибших; опыт не получает погибший, резерв не вычисляется из уже уменьшенного
списка так, чтобы погибший или участник сменил категорию. Дроби H1 сохраняются.
Вещи погибших победителей и артефакты следуют разным принятым путям; удаление
героя не должно удалить или продублировать их записи.

Обычная экипировка между боями доступна лишь из множества `ordinary_item_ids`,
зафиксированного на выходе: склад и уже отправленные вещи погибших закрыты.
Этот признак походной собственности независим от `hero_id`/слота: снятие или
передача не удаляет ID из множества, а `hero_id=0` само по себе не даёт доступ
ко всему складу. Передача/смена доспеха переносит остаток самой вещи.
После победы вещи, надетые на погибшего и отправленные на склад, удаляются
из `ordinary_item_ids` в той же транзакции. Свободная вещь рюкзака остаётся
походной: прежний владелец не превращает её автоматически в защищённый склад.
При полном поражении удалить все оставшиеся `ordinary_item_ids`, включая
снятые вещи с `hero_id=0`; остальные складские/резервные вещи сохраняются.
При раннем/финальном выходе все оставшиеся вещи сохраняются и ограничение
доступа снимается. Валидатор запрещает ID несуществующей/резервной вещи в этом
множестве и надетую на участника вещь, которая в множество не входит.

Все постоянные мутации сохраняются до публикации. Ошибка записи сохраняет
старый опубликованный профиль и candidate для retry; UI блокирует новые
переходы/покупки/экипировку. Retry пишет тот же candidate, не повторяет RNG,
receipt, услугу или переработку. При process crash загружается последняя
успешная точка; точное продолжение середины боя не обещается.

## 4. Артефакты и боевой адаптер

Экземпляр походного артефакта: `artifact_id`, `definition_id`, `stack_count`,
`hero_id` (0 — общий рюкзак), `slot` (0 для рюкзака; 1–3 для героя). ID артефактов
отделены от ID обычных вещей; в одной записи ровно один владелец/место.
Для неогненных `stack_count=1`; огненные 1–3. У героя уникальны слот и definition.
Отдельный склад походных артефактов в хабе отсутствует.

Объединение — атомарная отдельная операция, которая может сопровождать попытку
экипировки такой же Искры: известные разные ID, один тип, допустимые владельцы,
сумма ≤3. Сохраняется ID предмета-получателя, поглощённый ID удаляется навсегда;
`next_artifact_id` не уменьшается. При 2+2 или 3+1 полный отказ, без частичного
переноса и удаления. Перемещение объединённого предмета сохраняет stack_count.
Неогненный повтор не подменяет/не выбрасывает уже надетый предмет автоматически.

Переработка считает вложенные копии всех надетых и лежащих артефактов один раз;
награда финала учитывается отдельным слагаемым. Сохранение фазы `hub` не содержит
непереработанные экземпляры. При поражении исчезают все походные экземпляры,
а не только экипировка последнего погибшего. Исторический итог хранит value-итоги,
не второй активный инвентарь. У копирования/restore нет генерации новых ID.

Battle adapter получает неизменяемое описание активных артефактов, stack_count
и постоянные ID, создаёт полностью независимый runtime. Не добавлять бонусы
напрямую в HP/броню профиля при каждом открытии карточки. Добавочный огонь —
источник общего расчёта обычной атаки; реакции/действия мага не наследуют его
из общего оружейного stat. Признак обычной атаки задаётся явной capability,
не строковым поиском названия/класса.

Порядок эффектов, HP-gate, иммунитеты и руны принадлежат принятому каталогу и
[K17](STATUS_EFFECTS_NEXT.md). Реакции артефактов создают команды в текущей очереди;
callback не меняет state сам. Смерть/FAULTED останавливают несовместимые хвосты.
Жатва использует причинный результат прямого исходного hit, не любое событие
смерти в общей цепи и не проверку «цель исчезла к концу очереди».

Копирование/codec должны включать definition/version, stack_count, владельцев,
ограничители срабатываний и причинные поля, которые переживают границу команды.
Preview/restore/live worker получают тот же runtime; нет скрытого источника
эффектов из UI или живого профиля. Равенство проверяется по полному snapshot,
событиям/шагам, вещам, RNG и counters; revision-only кэш мира запрещён.

с явной artifact capability; старые версии продолжают читаться точно.

бонусы или ремонт; число restored копий и значения counters совпадают точно.

A представления: F5 переводится на простое главное меню с продолжением
существующего профиля и входом в хаб/сохранённый поход. Новый профиль создаётся
только при отсутствии файла по прежнему безопасному пути H1; автоматического
сброса повреждённого профиля и кнопки удаления прогресса этот пакет не добавляет.
Карта показывает все узлы/связи, отдельно текущие доступные выборы, полосу
HP/брони, походные награды и панель распределения; UI не раскрывает скрытые
данные из сохранённого плана через подсказки/карточки дальних узлов.

## 5. Профиль schema2 и совместимость

Сохранить путь `user://hero-hub-v1.save`; новый envelope имеет явный формат
`hero-hub-v2` и payload schema2. Читатель поддерживает обе известные версии,
писатель новой версии пишет только schema2. SHA-256/лимит размера/строгая shape
валидация сохраняются. Нельзя превращать неизвестную/повреждённую версию в новый
профиль или угадывать поля. Поля schema1 без изменений переносятся в schema2;
эссенция=0, поход отсутствует, новые счётчики получают проверенные начальные значения.

Schema1 в `hub` мигрирует и атомарно записывается до разрешения новых действий.
Schema1 в `battle` сохраняет старую контрольную точку и правила H1: загрузка
повторяет прежний одиночный бой, исход применяется старым путём один раз,
после возврата доступен новый выход U14. Не превращать незавершённый старый бой
в первую комнату произвольной карты; не лечить/не нанимать/не перерабатывать
при самой миграции. При отказе записи сохраняется исходный файл и возможность retry.

Schema2 валидирует profile/phase согласованно с run/receipt, граф, доступность
посещённого маршрута, версии каталогов, уникальность ID/слотов, стеки, ресурсы
и начисления. Технические пределы чисел проверяются до суммы/мутации; отказ
не обрезает добычу и не списывает предметы. Размер файла/переполнение — явная
ошибка, не повод отбрасывать героев или артефакты. D4-save не читается/не меняется.

## 6. Единый пакет реализации и приёмка

Реализацию запускать отдельным поручением; Q14-T1 закрыт принятой поправкой
лимита выходов безопасной точки. Один кодер в общем checkout; ведущий владеет границами
профиля/сохранения, генератора, очереди и preview. Независимое ревью — после
записи на фиксированном результате. Промежуточные технические этапы могут иметь
логические коммиты; пользователь получает один полный цикл для плейтеста.

1. Модель/генератор/переходы и миграция: законченные тестируемые value-операции,
   инварианты графа, однократный receipt и инвентарь. Это не готовый игровой U14.
2. Боевой адаптер и шесть артефактов: реальные команды + copy/codec/worker/preview,
   данные встреч/полей с validator; никаких mock-побед в пользовательском пути.
3. Меню → хаб → карта → комнаты → итог → хаб, настоящий ввод и сохранение;
   сквозные победа, ранний выход, поражение, перезапуск/отказ записи.

| Область | Обязательная проверка |
|---|---|
| Генерация | Повтор seed даёт полный одинаковый план; разные seed изменяют варианты; все пути соблюдают структуру, ни одного висячего узла; ограниченный детерминированный генератор не зависает на подборе |
| Видимость | Вся схема/типы видны; точные будущие условия скрыты и недоступны для выбора; раскрытие не потребляет RNG; reload сохраняет выбор и раскрытие |
| Переходы | Неверный/повторный node ID, пропуск слоя, второй результат/услуга/награда отвергаются без мутации; после лагеря нельзя вернуться за второй услугой |
| Ресурсы | HP/броня переносятся, лечение хаба только на выходе, снятие состояний не даёт тиков; новый бой K18; снятие/передача доспеха не ремонтирует; снятый доспех теряется при поражении, ранее отправленный на склад сохраняется; склад недоступен из карты |
| Артефакты | 1+1/2+1, отказы 2+2/3+1 без потерь, неделимость/целая передача, запрет двух одинаковых; смерть владельца/рюкзак/поражение и эссенция по вложенным копиям |
| Боевой эффект | Каждый отдельный триггер, неподходящий тип действия/цель, порядок всех трёх рун, 50% брони до удара, иммунитеты, настоящий direct kill против падения/тика; preview/live/оба worker |
| XP/итог | Выжившие/резерв/погибшие, рост и дроби, каждая победа до финала, поражение после прежних побед, финальная награда и переработка ровно раз |
| Restore | Каждая фаза, начало боя/seed/расстановка, pending награда и camp_departure; нет reroll/двойной награды; schema1 hub/battle, corrupt/unknown, ошибка записи/retry |
| UI/полный путь | Клики/клавиши/scroll в SubViewport, PNG без перекрытий; полный бой реальными командами, оба выхода и полный проигрыш; блокировки pending/FAULTED |

Адресные новые runner добавляются в `tools/demo/isolate.py` и [TESTING](TESTING.md)
при реализации; перечисление здесь не объявляет их существующими.
После адресных проверок обязательны import/startup, `--check --full` и
`--render-check` по TESTING, независимое ревью фиксированного результата.
Прежний initiative_ui viewport FAIL сравнивается с base, не исключается молча;
новые ошибки/leaks недопустимы. Техническая проверка не заменяет общий плейтест.
