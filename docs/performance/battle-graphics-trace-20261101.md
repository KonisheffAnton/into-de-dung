## Два наблюдаемых случая

У29 из30 пиков кадр render-complete за13,5648–13,9356мс до display timestamp
предыдущего кадра. Каждый длинный интервал соответствует одному VSyncDPC
target4355, FrameNumber увеличивается на1. Интервалы в `FrameQPCTime` тоже
удлинены; следующий VSync-интервал укорачивается до8,2596–13,2585мс.
Времена окончания/начала display совпадают с выбранными VSyncDPC с погрешностью
не более0,0007/0,0001мс. Само событие DPC наступает через0,0710–0,1114мс после
его `FrameQPCTime` во всех30 случаях.

Это локализует29 выбросов после готовности кадра, но не определяет, почему
задержался VSync. PresentMon использует sync DPC для screen time: корреляция
с этим событием не является независимым физическим измерением монитора.
Семантика — [исходник PresentMon2.6](https://github.com/GameTechDev/PresentMon/blob/v2.6.0/PresentData/PresentMonTraceConsumer.cpp).

Самый длинный display-интервал33,0262мс (CSV1576) пересекает два VSync.
Его render-complete позже предыдущего display timestamp на16,2875мс:
`msUntilRenderComplete=56,7873`, при `msGPUActive=4,9507`.
Следующий Present API занимает33,6651мс. В окружающем окне233мс есть113
AllocationFault и113 PageInAllocation (PID4), 196 PagingQueuePacket/Start:
190 имеют PID1420, остальные6 — PID4. PID1420 сопоставлен с dwm.exe по живому
процессу, созданному до начала записи; это не устанавливает владельца каждой
allocation. Второй выбранный пик24,9637мс (CSV5180) тоже окружён paging:
101 AllocationFault, 100 PageInAllocation, 211 PagingQueuePacket/Start
(170 с PID36224, 41 с PID4). Имя завершившегося PID36224 не установлено.
Это корреляция с операциями памяти/очереди GPU, а не доказательство нехватки
VRAM или причины каждого ожидания. У CSV640/2824/3429 таких paging-событий
в выбранных окнах нет. Сам факт paging не доказывает
дефицит памяти: операции включают также обновления GPU virtual address.
[Описание Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/device-paging-queues).

## Подготовка повторного сбора

Для причины ожиданий нужны одновременно текущие графические события и CPU
scheduler/ISR/DPC/stacks. Новый helper `capture_battle_kernel.py` добавляет
именованный WPR GeneralProfile.Light+CPU вокруг уже проверенного
`run_autonomous_soak.py --events`, который выполняет естественный бой32.
Это новая диагностика по выявленному пробелу покрытия, не изменение игры.
Пользователь затем выполнил этот повышенный путь: результат приведён ниже.

Python parse, 18 mock tests и `--plan-only` прошли. Независимое ревью:
APPROVE_WITH_LIMITATIONS. Исправлен найденный ревьюером путь ошибки вывода,
который мог пропустить остановку WPR. Проверены ошибки старта/остановки,
прерывание, восстановление argv, отказ без прав и коллизии файлов.
Все команды очистки адресуют собственную именованную сессию. Привязка отчёта
внутреннего runner предполагает один одновременный сбор; это не доказательство
идентичности при постороннем конкурентном запуске. Наличие нужных событий
проверялось отдельно в полученной записи.
