# Каталог пакетов расширяемости M1–M4

Спецификации подготовлены 2026-09-15 и ещё не реализованы. Редакция навигации
2026-09-20 сохраняет их содержание, но убирает самостоятельную очередь работ.
Рекомендуемый следующий шаг и порядок задаёт только §7 [DESIGN_DIRECTION](DESIGN_DIRECTION.md).
Ни этот каталог, ни прежний план не запускаются автоматически. Старый порядок
с M1 первым сохранён в [архиве](MODULARITY_PLAN.history-20260920.md).

## Цель и исходное положение

Варианты существующих механик должны задаваться проверяемыми определениями;
принципиально новое поведение — отдельным небольшим обработчиком с явным контрактом.
Характеристики, очередь, позиции, управление ходами и UI не должны получать
новые специальные ветки для каждого варианта предмета или атаки.

Существующие API и их ограничения перечислены в [ARCHITECTURE](ARCHITECTURE.md).
Успешные тесты нынешнего боя подтверждают его поведение, а не универсальность API.

Число в общем правиле само по себе не дефект. Стоимость нынешней атаки 1 main —
согласованный контракт. Извлекаем параметры контента и точки расширения там,
где нужен новый вариант, сохраняя один источник каждого правила.

## Состав каталога

M1 — определение помощника; M2a — выделение расчёта нынешней атаки;
M2b — удар в спину; M3 — общий контракт применения предметов;
M4 — новое свойство/эффект под конкретный согласованный сценарий.
Номера обозначают пакеты, а не обязательную последовательность исполнения.

## M1 — параметры помощника

### Границы

Вынести базовые характеристики помощника и параметры его отображаемого имени
из команды призыва в типизированное Resource-определение, связанное с определением
печати. Рабочее имя нового типа — `SummonDefinition`; это предложение, такого API
пока нет. Если нужен общий UnitDefinition, обосновать его конкретным повторным
использованием; не переносить всех исходных героев и полигон в этом же изменении.

Существующая печать по умолчанию сохраняет ровно нынешние значения: HP 16,
броня 0, сила 4, оружие 2, impact 3, balance max 5, move 4, main max 1,
bonus max 1, дальность 1. Другой набор параметров проверяется тестовым определением,
без добавления второго игрового предмета или изменения стартового боя.

Не менять цену/заряды/геометрию призыва, лимит владельца, pending, admission,
refill, BT, срок, cleanup, исход боя или стратегию ID. Не объединять флакон и печать.
Общий механизм действий предмета относится к M3; M1 сохраняет совместимость
нынешнего use_summon и задаёт однозначное разрешение старого определения.

### Контракты, которые ведущий фиксирует до передачи кода

1. Определение хранит только базовые данные. ID, faction, cell, владелец, pending,
   текущее HP/действия/заряды принадлежат runtime; их нельзя принести шаблоном.
2. Разрешённые stats и типы, конечность/границы значений, обязательные поля,
   ошибки и пределы размера проверяются до оплаты и создания runtime.
   Ошибочные/неизвестные данные не подменяются молча стандартным помощником.
3. Определение фиксируется проверенной изолированной копией при сборке контекста
   боя. Мутация исходного Resource после этого не меняет бой. Экземпляры помощников
   не разделяют изменяемые StatsBag/Vitals/ActionResources; getters не выдают
   доступ к изменяемому определению внутри боя. Оплата, snapshot и callback-check
   используют одну и ту же зафиксированную версию.
4. Snapshot переносит все влияющие значения, а не один resource_path/id.
   Ведущий заранее описывает формат, deep-copy и поддержку прогноза, raw validation
   до allocation, restore без equip/refill и неизменность исходного состояния.
5. Исторические item v1/v2/v3 и unit v1/v2/v3 остаются читаемыми; прежние формы
   сохраняют точные canonical bytes. Для нового набора данных при необходимости
   добавить новую явно именованную версию, не переопределять значение v3.
   Legacy v3 use_summon означает документированный исходный шаблон, без обращения
   к изменяемому внешнему каталогу. Точную политику выбора writer/сравнения catalogue
   описать до реализации; неизвестная версия/конфликт данных дают явный отказ.
6. Команда продолжает атомарно создавать полного участника через ActionQueue,
   с прежними main/charge, revision, событиями и сохранением исполненного prefix.
   Не допускать создания лишь фигуры/board entry вместо полноценного помощника.

### Приёмка M1

- Исходный шаблон даёт прежние stats, события, ресурсы, admission и исход боя.
- Изменение HP/силы в тестовом определении даёт соответствующее существо через
  настоящую команду, без изменения команды, turn flow, BT или UI для этого варианта.
- Два владельца и повторный призыв после гибели имеют независимый runtime.
  Изменение исходного Resource/одного экземпляра не меняет другой или изолированный бой.
- Неверные данные/версии/ссылки отклоняются без оплаты, allocation побочных runtime,
  occupancy, событий, RNG и revision. Проверены обычный отказ и stale command.
- Live → snapshot → restore сохраняет полный нестандартный шаблон и pending/ready;
  старые fixtures/fingerprints остаются совместимыми. Никакого refill на restore.
- AttackForecast при нестандартных helpers и ещё не использованной печати переносит
  определения, состав, заряды и admission; полное parity со свежим реальным submit,
  включая летальный удар. Влияет не только уже созданный helper, но и definition.
- Callback/лимит FAULTED сохраняют исполненный prefix; sink после drain не мутирует
  игру. Призыв и детерминированные проверки не расходуют RNG/глобальные ID.
- Сохраняются immediate occupancy, запрет исходящих действий pending helper,
  первый командный refill, управление игроком, enemy BT, смерть/замена/исход/cleanup.

Пакет исполнителю и критическая интеграция — по [CODEX_WORKFLOW](CODEX_WORKFLOW.md).

## M2a — выделение расчёта нынешней атаки

Сохранить AttackCommand ответственным за допуск, оплату, исполнение и очередь;
выделить чистый расчёт из проверенных входных значений. Он возвращает рассчитанные
величины и структурированное объяснение применённых правил, не мутирует stats,
board/RNG и не выпускает события. Цена нынешней атаки остаётся 1 main.

Явно разделить базу B = strength + weapon, добавки к прямому удару до брони,
броню, нижнюю границу урона/охранную стойку, balance impact и базу последствий.
Сохранить существующие порядок операций, float-результаты и clamps, включая
legacy профили; механическое переупорядочивание формулы без проверки недопустимо.
Collision/fall не получают модификаторы прямого удара автоматически.

AttackDefinition получает только необходимые типизированные параметры/модификаторы.
Для нового типа есть единый явный контракт проверки и копирования; не исполнять
произвольные скрипты/Callable из snapshot. Фиксировать порядок модификаторов и
повторного применения, отклонять неизвестные данные. Конкретные имена API — в ТЗ M2a.
Forecast продолжает исполнять настоящую команду; UI читает результат, не считает урон.

Приёмка: полное сравнение текущих профилей до/после, включая armor/guard/height,
impact/collision/fall, отказы, RNG, события, ресурсы, revision, FAULTED prefix и
изолированный forecast. Не вводить спину, крит, пробивание или новые атаки в M2a.

## M2b — условный модификатор удара в спину

Реализовать только §3 TACTICAL_DESIGN_NEXT через подготовленный механизм:
одна соседняя тыльная клетка, фиксированное логическое направление команды,
включая helpers. До кода указать точные grid-векторы обеих команд; screen/camera
координаты не участвуют. Бонус +50% B до брони, складывается с высотой относительно B.
При B=10, высоте +20% и спине +50% прямой удар до брони равен 17, не 18.
Спина не усиливает impact, collision или fall; постоянная STRENGTH не меняется.
Будущий крит x2 до брони и x2 impact остаётся дизайном, базовых критов нет.

UI показывает тыл и объясняет бонус в прогнозе. Проверить перед/бок/тыл обеих
команд, высоты и броню/стойку, движение/толчок до атаки, обычных бойцов и helpers,
full forecast parity и UI настоящим input в отдельном SubViewport.
ИИ обязан корректно исполнять ту же атаку с бонусом; специальный поиск пути к спине
и улучшение стратегии в этот срез не входят и не объявляются автоматическими.

Критерий расширяемости: новый модификатор не требует специальной логики в board,
turn flow, очереди последствий и отдельной формулы UI. Изменение коэффициента
меняет только данные определения. Новое условие добавляет небольшой обработчик
и его поддержку validation/copy, а не дублирует весь расчёт атаки.

## M3 — общий контракт действия предмета

На уже работающих лечении и призыве выделить типизированное описание применения:
цель, стоимость, параметры, доступность с причиной отказа, создание команды.
Реальная команда повторно валидирует состояние при submit; UI/BT не оплачивают
действие и не меняют ресурсы. Флакон и печать остаются разными предметами/командами.

Миграция старых use_* полей, их snapshot и catalogue проверяется явно. Известные
виды действий регистрируются с validation/copy/restore; произвольный класс не
получает capability прогноза автоматически. UI берёт общие цену/заряды/причину,
особый выбор клетки остаётся типизированным режимом цели. Проверить клавиши,
disabled reasons, очистку режима, страницы и scrolling через SubViewport.
Не добавлять редактор, смешанный heal+summon, третий предмет или forecast применения.

## M4 — расширение под следующий утверждённый механизм

Не создавать заранее каталог всех возможных stats, DSL, плагины, ECS или общий
движок статусов. При первом новом stat согласовать append-only ID и единый
источник его допустимости, убрать дублирование границ validators без ослабления
raw checks. При новом эффекте определить обработчик/codec, источник, lifetime,
активацию/снятие, cleanup, события и full snapshot capability вместе.

Пробивание, состояния и эффекты клеток остаются требованиями из
MECHANICS_REQUIREMENTS; их числа/порядок/длительности требуют точного ТЗ перед
зависимым срезом. Приоритет между ними пока не выбран. Крит/Оппортунист/окружение,
расстановка/новые цепи/падения и камера не входят в M1–M3.

## Общая приёмка

Сохранить действующие контракты боя, прогноза, стойки, лечения и призыва из
[PROJECT_CONTEXT](PROJECT_CONTEXT.md). Адресные критерии пакетов выше дополняют
обязательные проверки из [TESTING](TESTING.md); числа старых прогонов не являются
приёмкой нового изменения. Порядок сдачи и история — [CODEX_WORKFLOW](CODEX_WORKFLOW.md).
