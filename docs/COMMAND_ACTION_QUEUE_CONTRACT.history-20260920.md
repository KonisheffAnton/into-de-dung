# Шаг 0.5 — контракт Command / ActionQueue для Move, Attack, Push

Дата: 2026-09-13. Редакция: draft-2 (после независимого ревью). База исследования: `main`,
`b102678b28957e6d17282878dea19d3946d9f570` + существующие незакоммиченные документы.
**Документ описывает предложенный API 0.5; реализованы пакеты P01, P02, ownership P03a и snapshot/collection P03b.**
После указания пользователя «Давай тут пока» выполнен P01 (смерть/occupancy), см. раздел 10.
P02 реализован по отдельному указанию пользователя, см. раздел 11; P03a — раздел 12; P03b — раздел 13. P04 и последующие пакеты не реализованы.
Зависимые вопросы не заменяются предположениями.
Процесс: [CODEX_WORKFLOW.md](CODEX_WORKFLOW.md), требования: [MECHANICS_REQUIREMENTS.md](MECHANICS_REQUIREMENTS.md).

## 1. Решения и границы

Подтверждено пользователем: команды ходят поочерёдно; порядок персонажей своей команды
игрок выбирает сам; инициатива не определяет ходы. Переключение выделения не является
началом/концом командного хода или раунда.

Также подтверждено в текущей задаче: три отдельных ресурса — очки перемещения,
основного и дополнительного действия; атака расходует **одно очко основного действия**.
Это заменяет старые общий пул Move/Attack и булево право `has_attacked`.
Остались уточнения:

| Решение | Что заблокировано до ответа |
|---|---|
| G-1: можно ли вернуться к частично походившему персонажу после действий другого? | Модель завершённой активации, разрешения на повторное действие, влияние переключения на остатки ресурсов |
| G-2a: можно ли двигаться после атаки при оставшихся очках перемещения? | Дополнительное ограничение Move после Attack и тест Move→Attack→Move |
| G-2b: чем заданы максимумы основного/дополнительного действия, сколько их в первом срезе и когда пополнять? | Инициализация/пополнение ресурсов; предложено начало хода команды и максимумы из характеристик |

Ни `move_points_left`, ни старый `has_attacked` не решают открытые вопросы.
Ниже определены инварианты расхода; значения максимумов и правила завершения не имеют default.
Рекомендация ведущего по G-1: разрешить возврат, сохраняя остатки ресурсов. Переключение
не откатывает действия и не требует восстановления карты; snapshot нужен отдельно для preview.
У пользователя запрошено подтверждение рекомендации. До ответа не кодировать зависимую политику.

Дополнительные предложения для согласования перед пакетом Push: одноклеточный толчок;
при столкновении урон обоим без продвижения и без автоматического толчка блокирующего;
настраиваемые величины урона о стену/юнита/за перепад высоты и правило учёта брони.
Код содержит геометрию, но не утверждённые числовые формулы. Тестовые числа ниже — фикстуры.
Цепное проталкивание и дистанция от IMPACT_POWER из AUDIT D-6.2 остаются открытым расширением;
этот контракт предлагает исключить их из минимального среза, а не считать D-6.2 полностью закрытым.

**0.5 владеет:** валидацией команд, исполнением, списанием разрешённого ресурса,
цепью последствий/реакций, событиями результата, смертью/occupancy, изолированной симуляцией.
**0.6 владеет:** активной командой, выбором/допуском персонажа, явными границами командного
хода/раунда, пополнением ресурсов, завершением боя и разрешением следующего ввода.
Кто начинает бой, как заканчивает активацию враг, исход гибели обеих команд — решения для 0.6.
Очередь не вызывает `UnitState.begin_turn()`, не сбрасывает ресурсы при выделении и не
использует `InitiativeTimeline`. Победа проверяется 0.6 только после завершения всей цепочки.
BT, статусы, огонь, сопротивления/пробивание, награды, полный save-game и UI-комбо не входят в 0.5.
Utility AI сохраняется; его адаптер впоследствии переводит намерения в те же команды.

## 2. API на base commit (изменения P01 — в разделе 10)

Пути ниже относительно корня проекта. Комментарии и старые Interface Cards местами устарели;
источником фактов здесь служит реализация, а не обещания в комментариях.

| Существующий API | Поведение и ограничение |
|---|---|
| `BattleBoard.move_unit(unit: UnitState, to_cell: Vector2i) -> bool` | Обновляет cell/height/occupancy/version, проверяет границы и сырую occupancy; не проверяет terrain, высоту перехода или стоимость. Оставшаяся запись умершего блокирует движение |
| `clear_occupancy(unit)`, `get_unit_by_id(id: int)`, `can_enter(cell, for_unit)`, `make_data_provider(for_unit)` | Очистка сохраняет труп в реестре; `can_enter` игнорирует умершего, но автоматической очистки по смерти нет. Для пути нужен provider своей доски |
| `GridPathfinder.configure(bounds, provider, max_height_step=1)`, `find_path(from, to) -> Array[Vector2i]` | Путь включает старт, только четыре направления; стоимость входа, симметричный предел перепада высот. Сортировка frontier сравнивает только стоимость — полного tie-break нет |
| `UnitState.move_points_left`, `has_attacked`, `spend_move_points(amount)`, `can_attack()`, `begin_turn()` | Остаток движения, флаг одной атаки, списание с clamp; `can_attack` проверяет жизнь и флаг. Это старая модель, не подтверждение G-2 |
| `Vitals.apply_damage(amount) -> float`, `heal(amount) -> float`, `add_impact(amount) -> bool` | Возвращают фактическое изменение; `died` при переходе alive→dead один раз; лечение умершего запрещено; слом баланса сбрасывает его в 0 |
| `DamageCalculator.calculate(attacker, target, attacker_cell, target_cell, base_damage, impact_power, board, max_height_step=1) -> DamageInfo` | Чистая формула `max(0, base + STRENGTH - ARMOR)` и геометрический прогноз; при null attacker расчёт не выполняется |
| `DamageCalculator.apply(info: DamageInfo, sink: EventSink=null) -> void` | HP, затем баланс только живому, события; не применяет Push/коллизии/падение. Повторный вызов на умершем повторяет `unit_died` |
| `PushResolver.resolve_push(board, target, target_cell, direction, max_height_step=1) -> PushResult` | Один шаг; bounds→wall→height→живой occupant→lethal terrain→свободная клетка. Направление по доминирующей оси, при равенстве X. Вниз разрешено, `fall_height` только данные |
| `PushResult.Outcome` | `MOVED`, `BLOCKED`, `COLLISION`, `FELL`; при collision цель остаётся на месте, есть `blocker`; FELL включает VOID/HAZARD и край доски |
| `ActionPreview.build(...) -> DamageInfo` | Только делегирует calculate; полная цепь не исполняется |
| `EventSink.unit_damaged(unit, amount, source: Variant)` и другие методы | Инжектируемый сток; базовый класс ничего не делает. Отдельного класса `NullEventSink` нет; `RecordingEventSink` хранит аргументы, в том числе ссылки на юнитов |
| `BattleBoard.to_dict/from_dict`, `UnitState.to_dict/from_dict` | Сохраняют часть состояния; загрузка меняет глобальный `UnitId` counter. Board version не сохраняется; inventory/equipment не входят в UnitState |
| `StatsBag.to_dict()` | Только базы, без модификаторов; это не снимок симуляции |
| `ItemDef/Item`, `ItemInstance`, `ItemOwnerState` | P03a разделяет определения и runtime двух эффектов; общий ledger inventory/equipment, стабильные локальные ids. Core heal содержит данные; прежнее лечение только в test-only LegacyItemDemoSink. Legacy load остаётся fresh-equip |

Исходники: `scripts/core/{board,pathfinding,units,combat,events,stats,items,inventory}/`.
Command, ActionQueue, ActionContext, RngService и перечисленные далее DTO отсутствуют.
SimulationSnapshot реализован только как board-only фасад P02 (раздел 11), без контекста,
очереди и предметов. Статусы Verified прошлых модулей не распространяются на предлагаемый 0.5.

## 3. Предлагаемые Interface Cards

Все следующие имена/сигнатуры **новые**. Runtime и DTO — строго типизированные `RefCounted`;
Resource — только неизменяемые определения. Числовые UnitId передаются вместо живых ссылок.
Массивы/DTO запросов копируются при приёме; вызывающий код не может изменить принятую команду.

| Новый тип / метод | Контракт |
|---|---|
| `Command` | Неизменяемый payload: `kind: StringName`, actor/target id, явный путь либо параметры намерения. `validate(context: ActionContext) -> CommandValidation` без мутаций/RNG/событий; `execute(context: ActionContext) -> CommandStepResult` вызывается только очередью |
| `MoveCommand` | Actor id, `path: Array[Vector2i]` с исходной клеткой. Один запрос может идти несколько рёбер; каждая достигнутая клетка — отдельная граница последствий |
| `AttackCommand` | Actor/target id, ожидаемые клетки, id неизменяемого определения атаки. UI не передаёт готовый урон или доверенный DamageInfo. Определение/тестовая фикстура задаёт base/impact/range/max_height_step |
| `PushCommand` | Внутренняя команда: target id, ожидаемая исходная клетка, направление, `DamageSource`, id настроек последствий. Не расходует добровольные ресурсы и не требует активной команды цели |
| `ActionContext` | Владеет одним BattleBoard и battle runtime: ресурсами действий после G-1/G-2, экземплярами предметов/реакций, RNG, номером ревизии и последовательностями. Инжектирует rules/admission, локальную обработку событий и внешний presentation sink |
| `ActionQueue.submit(command: Command, context: ActionContext) -> ActionReceipt` | Синхронно исполняет одну корневую команду до опустошения её последствий. В 0.5 нет фонового исполнения/await анимации. Внешний submit во время выполнения возвращает BUSY; отдельного публичного обхода через push нет |
| `ReactionHandler.collect(event: ActionEvent, context: ActionContext) -> Array[Command]` | Читает состояние, возвращает команды; не лечит/не наносит урон/не двигает непосредственно и не вызывает submit. Изменения собственного runtime и RNG тоже выполняются командами |
| `ActionQueue.preview(command: Command, context: ActionContext) -> PreviewResult` | Только при idle: проверяет snapshot capability, создаёт изолированные контекст **и новую очередь**, вызывает на ней тот же submit; возвращает результат, изменения состояния, value-журнал и PreviewToken |
| `ActionQueue.confirm_preview(command: Command, token: PreviewToken, context: ActionContext) -> ActionReceipt` | Единственный путь подтверждения из UI/адаптера игрового ввода: проверяет token/preconditions, затем синхронно вызывает submit. Несовпадение даёт STALE_PREVIEW без мутаций |
| `SimulationSnapshot.capture(context) -> SnapshotResult`, `instantiate() -> ActionContext` | Независимые mutable объекты, сохранённые id и состояние RNG; без обращений к live-сигналам/глобальному счётчику. Явная ошибка при неподдерживаемом runtime |

`CommandValidation`: код причины и рассчитанная стоимость без резервирования:
Move — стоимость входов, Attack — 1 main/0 move/0 bonus. `CommandStepResult`: изменения, новые события,
обязательные последствия и необязательное продолжение. Эти внутренние методы не API для UI.
`ActionReceipt`: `root_id`, статус, reason, ревизии before/after, список результатов шагов,
упорядоченные `ActionEvent`. Статусы: APPLIED, REJECTED, INTERRUPTED, FAULTED.
Для дочернего действия дополнительно SKIPPED (например, цель уже умерла).
`PreviewResult`: receipt, snapshot/diff после симуляции, token;
ошибка снимка/FAULTED не превращается в правдоподобный прогноз частичного результата.

`ActionEvent` — значения, а не ссылки на меняющиеся UnitState:
`event_seq`, `root_id`, `command_seq`, `parent_event_seq`, kind, actor/target id,
source, from/to/attempted cell, before/after и фактическая величина изменения по типу события.
Раздельно фиксируются moved, pushed, push_blocked/collision/fell, damaged, healed,
balance_changed/broken, died. Причина перемещения позволяет будущим эффектам различать Move/Push.
Предметы слушают локальные ActionEvent; прежний EventSink — адаптер уведомлений для представления.
Глобальные подписчики, меняющие бой, должны быть мигрированы до подключения этого адаптера.

### Владение и сериализация

- BattleBoard остаётся владельцем позиций/occupancy и реестра UnitState. Команды не
  записывают cell/height напрямую. Vitals остаётся владельцем HP/баланса и перехода смерти.
- Предлагается `ActionResources : RefCounted`, принадлежащий UnitState: `move_left: float`,
  `main_left: int`, `bonus_left: int`, методы проверки/списания и versioned snapshot/serialization.
  Это один владелец остатков; старые move_points_left/has_attacked мигрируются или становятся
  совместимыми производными accessors, а не вторым ledger. Атака списывает main_left на 1;
  Move — move_left по стоимости входа; bonus_left сохраняется, но действий для него в 0.5 нет.
  Максимумы, пополнение и возможный запрет движения после атаки ждут G-2a/G-2b;
  если понадобится флаг запрета, он также входит в runtime и snapshot. Очередь списывает,
  0.6 пополняет в явной границе. Нельзя выводить запрет повторной атаки из has_attacked,
  если у персонажа ещё есть основные очки.
- Очередь владеет pending commands, busy/fault state и журналом одной цепи; sequence counters
  принадлежат контексту. Для preview создаётся новая очередь без ссылок на live pending,
  receipt, journal или callbacks. Live-очередь не используется как исполнитель симуляции.
  Один writer контекста;
  callbacks низкоуровневых сигналов не могут менять боевую логику. Анимации читают журнал.
- Общая `state_revision` меняется после изменения любого влияющего состояния, включая
  HP, ресурсы, предметы и RNG; одного `board_version` недостаточно. Пока очередь занята,
  flow, inventory UI и другие системы не мутируют этот контекст.
- Runtime получает versioned `to_dict/from_dict`; definition ids вместо Node/Callable/ссылок
  на UnitState. Старые enum только дополняются. Формат снимка симуляции отдельный от старого save.
- Каноническое представление: units по числовому UnitId; occupancy/клетки по (y,x);
  stats по числовому StatType; item/effect instances по stable instance id;
  RNG streams по имени; регистрации реакций по полному ключу из раздела 5.
  Dictionary преобразуются в массивы пар с сортировкой ключей (числовые численно,
  StringName/String по Unicode code point; смешанные типы ключей запрещены).
  Порядок семантических массивов сохраняется: path, trace, дочерние команды и порядок
  вычисления модификаторов. Modifier records имеют stable source/instance/local-slot id,
  сериализуются по этому ключу с явным evaluation_order; snapshot восстанавливает именно
  арифметический порядок оригинала, не пересортировывает float-операции при копировании.
  Изменение evaluation_order — изменение состояния, не эквивалентная перестановка map.
  Для canonical bytes: UTF-8, versioned type tags, фиксированное кодирование целых и
  конечных float без locale/округления (IEEE-754 binary64, little-endian, -0 нормализуется
  в +0), length-prefixed строки/массивы. NaN/INF в сохраняемом runtime — явная ошибка.
  Fingerprint — SHA-256 этих байтов; не hash Dictionary и не Godot instance_id.
  Для тестов сравниваются и канонические значения, чтобы ошибка кодирования не скрыла разницу.
- Сохранение/восстановление в 0.5 поддерживается только при idle, после всей цепи; при busy
  явный отказ. Сохраняются runtime, sequence counters, RNG и revision. Сохранение между
  микрошагами и восстановление callback/стека исполнения не входят в срез.
- `PreviewToken : RefCounted` — копируемый неизменяемый DTO с исходными battle_instance_id,
  state_revision, canonical state fingerprint, canonical command fingerprint,
  rules/definitions fingerprint и версией контракта. Token выдаётся только для успешного
  прогноза (APPLIED или ожидаемый INTERRUPTED), не для FAULTED/ошибки snapshot.
  confirm_preview сравнивает все поля с переданным контекстом и командой до мутаций/RNG;
  другая битва, изменённые HP/ресурсы/правила/команда или повторное подтверждение старой
  revision дают STALE_PREVIEW. Затем обычная validate и submit без окна внешних мутаций.
  BUSY проверяется первым. Raw submit нужен исполнителю preview и headless harness;
  UI и будущие gameplay adapters обязаны использовать confirm_preview, не обходить token.
  Повторно проигрывать старый DamageInfo или применять конечный snapshot preview нельзя.

## 4. Допуск, валидация, стоимость и отказ

0.6 позже инжектирует допуск выбранного персонажа для текущего командного хода;
0.5 в тестовой сцене получает явный допуск без реализации инициативы/активаций.
Допуск не заменяет проверку жизни, цели, доски и ресурсов. Правило допуска после
переключения намеренно не определено до G-1. Реакциям не нужен допуск игрока, но нужны
валидные происхождение/root id и состояние цели. Внешний запрос Push отклоняется.

Перед первым изменением корневой команды: известный kind и definition, конечные
неотрицательные числа (NaN/INF запрещены), валидные id/состояние, совпадение ожидаемых
клеток и ревизии, допуск, геометрия, доступный ресурс и поддержка настроек последствий.
На отказе: ноль мутаций доски, vitals, ресурсов, предметов, RNG, ревизий и domain events;
диагностика REJECTED возвращается вызывающему. Не происходит автоматического end turn.
Ошибки входа не должны исправляться clamp или незаметной заменой цели/маршрута.

**Move:** проверить весь явный путь и бюджет до первого шага: минимум одно ребро,
начало равно cell, только соседние клетки по четырём осям, bounds, occupancy/terrain,
перепад и сумма стоимости входа (старт не оплачивается). Provider берётся от своего board.
Перед каждым ребром повторная проверка актуального состояния; стоимость этого ребра
списывается ровно при успешном board.move_unit. После входа исполняются все его последствия
и реакции, затем продолжение. Если юнит погиб/перемещён реакцией или путь стал непроходим,
остаток прекращается с INTERRUPTED: пройденное и оплаченные рёбра сохраняются, остальные
не оплачиваются. Это успешное начало с прерыванием, а не REJECTED без мутаций.
HAZARD сейчас проходим и смертелен: предлагаем в Move применять его летальное последствие
после входа, как в Push; это не реализация периодического огня. VOID не является путём Move.

**Attack:** атакующий/цель живы, цель допустима по Faction и определению атаки, позиции
берутся из текущей доски и сверяются с запросом. Минимальная ближняя атака — один ортогональный
шаг; ограничения высоты задаются определением, не угадываются кодером. Нужно main_left >= 1;
атака списывает ровно 1 main, 0 move и 0 bonus. Возможный запрет движения после атаки
ждёт G-2a и не должен скрыто обнулять другой ресурс. Принятая атака оплачивается один раз перед эффектом; нулевой урон из-за брони
не является отказом. Дочерние push/урон/лечение не оплачивают атаку повторно.
Не вызывается повторная оплата/валидация пользовательского допуска для каждой реакции.

**Push:** повторно вычисляет PushResult по актуальной доске, не исполняет сохранённый
геометрический прогноз. Нулевая/неосевая direction и неизвестные настройки — ошибка;
умершая/исчезнувшая/уже перемещённая цель дочерней команды — SKIPPED с причиной.
BLOCKED и COLLISION — результаты исполнения с последствиями, а не отказ атаки.

Инвариантная ошибка после начала (невозможная occupancy, неизвестный внутренний command,
превышение лимита цепочки) — FAULTED с журналом выполненного префикса. Нет обещания общего
rollback и возврата потраченного при программной ошибке. Очередь блокирует следующий ввод,
0.6 не переключает команду и не объявляет победу; ведущий получает воспроизведение.
Лимит операций на root задаётся явно в rules, одинаков в preview/execute; цепь не обрезается
молча до «успеха». Валидация до старта должна ловить ожидаемые отказы, а не превращать их в FAULTED.

## 5. Порядок команд, последствий и реакций

Исполнение синхронное, без рекурсивного вызова execute из сигнала. Технический стек work
records принадлежит очереди: после атомарного шага она ставит перед продолжением
**обязательные последствия → собранные реакции → продолжение**, в указанном порядке.
Дочерняя цепь завершается до следующего sibling. Например: Attack → Push → collision damage
→ реакции collision damage → реакции Push → реакции Attack → следующий корневой запрос.
Реакции собираются из зафиксированных событий шага до запуска его детей; их цели/условия
повторно валидируются при выполнении. Для Move такая граница есть после каждого ребра.

Детерминированные ключи: события в документированном порядке ниже; реакции сортируются по
`(event_seq, priority ascending, owner_unit_id, effect_instance_id, local_index)`.
Идентичные ключи регистрации запрещены. Обязательные последствия имеют фиксированные роли
(например, pushed target раньше blocker); последовательности выдаёт контекст.
Не использовать порядок Dictionary, загрузки Resource, подписки сигналов, кадров или адреса объектов.
Путь уже явный; при построении пути адаптером нужен полный tie-break frontier
`(cost, cell.y, cell.x)` и фиксированный порядок соседей. Это планируемая правка, не гарантия текущего pathfinder.

### Атака и смерть

1. Оплатить разрешённую атаку; вычислить фактический урон общей чистой функцией.
2. Через Vitals снять HP. Если был alive→dead, немедленно освободить occupancy через
   BattleBoard, сохранив UnitState в реестре. Записать damaged (только при dealt > 0), затем died.
3. Только выжившей цели добавить impact; записать balance_changed при изменении,
   затем balance_broken при сломе. Сам Vitals уже сбрасывает баланс; второй reset запрещён.
4. При сломе у выжившей цели поставить обязательный PushCommand ровно один раз.
   Прямой смертельный урон не толкает труп. Затем идут реакции по правилам очереди.

Единственный источник domain-смерти — зафиксированный переход alive→dead, не повторная
проверка `not is_alive()`. `Vitals.died` можно использовать для внутренней очистки board;
нельзя одновременно публиковать смерть из этого callback и из apply. Подписчики реакций
видят освобождённую клетку. Повторный урон умершему, повторный cleanup или skipped push
не создают смерть/награду ещё раз. `heal` не воскрешает; revival вне 0.5.
Прямые вызовы старого apply в интегрированной сцене устраняются либо маршрутизируются
в тот же исполнитель, чтобы не было второго пути смерти/событий.

### Таблица Push — предлагаемая политика среза

| Исход резолвера | Исполнение до внешних реакций |
|---|---|
| MOVED | board.move_unit, pushed; если fall_height > 0 — обязательный урон от высоты по настройкам; затем реакции |
| BLOCKED (wall/height) | Позиция прежняя, push_blocked; обязательный урон толкаемому по настройкам; нет unit_pushed |
| COLLISION | Зафиксировать два id и оба запроса урона по состоянию столкновения; collision; урон сначала толкаемому, затем blocker, с cleanup после каждой смерти. Реакции первого урона ждут применения обоих. Никто не сдвигается даже при смерти blocker |
| FELL в существующую lethal клетку | board.move_unit в неё, pushed/fell; без окна реакции немедленно летальный исход через общий обработчик смерти; occupancy убрана |
| FELL за край | Не вызывать обычный move_unit с out-of-bounds. Предлагается board.finish_fall(unit, attempted_cell) с очисткой occupancy и сохранением последней допустимой cell/height у трупа; журнал fell хранит attempted_cell. Затем летальный исход; нет фиктивной occupancy за доской |

Для collision используется один внутренний атомарный `CollisionDamageCommand` с двумя
запросами: так второй участник получает заранее определённый урон до реакций первого.
Урон коллизии/падения не добавляет STRENGTH автора повторно и не вызывает новый impact
без явного правила. `PushDamageRules` — новое immutable определение параметров wall/unit/fall
и armor mode; без утверждённых значений production-запрос отклоняется до старта root.
Летальный terrain/выход за край обходит броню как исход падения, не как число «999999».
Числа и пороги обычного урона от высоты в коде отсутствуют и здесь не назначаются.

Реакции на lethal hit могут существовать, но лечение умершего будет SKIPPED/no effect.
Death effect, нацеленный на другого живого юнита, допускается очередью; наличие такого
контента не заявляется. Правила одновременной гибели команд принадлежат 0.6, после drain.

## 6. Preview и зависимость от C-3

Preview исполняет **тот же алгоритм очереди**, но новый экземпляр ActionQueue на независимом
ActionContext; изолированы и данные боя, и изменяемое состояние исполнения. Внешний UI/audio sink
может быть нулевым; локальные влияющие реакции отключать нельзя. Сравнение с execute:
HP/баланс/жизнь, cell/height/occupancy, ресурсы действий, характеристики и runtime эффектов,
RNG после цепи, порядок/value-поля событий и результат команд. Не сравниваются адреса объектов.
Одинаковый результат требуется при одинаковых исходных snapshot, payload и rules/version.

Снимок включает: размеры/terrain/высоты, реестр живых и мёртвых с id, occupancy,
полные базы **и модификаторы** stats с порядком/источниками, vitals, согласованные ресурсы
действий, владельцев и экземпляры предметов/effects, внутренние счётчики/заряды,
текущий допуск и его revision, rules/definitions fingerprint, sequence counters,
состояние каждого именованного RNG-потока. Будущие эффекты клеток/статусы обязаны
зарегистрировать такое же копирование до подключения к симуляции; сейчас их систем нет.

Не использовать `BattleBoard.from_dict(board.to_dict())` как полноценный clone:
он теряет modifiers/items, меняет глобальный UnitId и восстанавливает другую version.
Нужен отдельный явный путь snapshot без `UnitState.create/UnitId.next` и без signal listeners
живой сцены. Для 0.5 новые юниты не создаются, id сохраняются; live UnitId counter не трогается
даже временно. Временное изменение с последующим restore не считается изоляцией.

**C-3 — обязательная зависимость полного preview**, хотя большая миграция инвентаря была
запланирована на 0.8. Предлагается перенести вперёд ограниченный Def/Instance split только
для влияющих эффектов первого среза: stat modifier и существующего heal-on-damage.
Определение разделяемое immutable, отдельный `ItemInstance/ItemEffectRuntime` на каждого
владельца и копию; stable instance id; локальная регистрация реакции, лечение через
внутренний HealCommand. Никаких `_bound_unit` в Resource, глобальных подписок или записи item_id
при equip. Snapshot восстанавливает уже имеющиеся modifiers ровно один раз, затем привязывает
runtime без повторного on_equip; сценарий load/equip проверяет отсутствие удвоения.

До этого допустим только промежуточный срез на явно проверенной сцене без влияющих предметов;
он не закрывает 0.5 и не считается полным preview. Неизвестный активный эффект даёт
SNAPSHOT_UNSUPPORTED с id, а не молча исчезает из расчёта. Тот же capability gate ограничивает
интегрированное исполнение сцены, чтобы preview и execute не имели разных поддерживаемых правил.
`Resource.duplicate(true)` не решает C-3: не определяет владение/подписки и нарушает R-1.

RngService пока отсутствует (план 0.10). В 0.5 нужен минимальный инжектируемый порт состояния
потоков с clone/to_dict/from_dict, без глобального rand и без randomize; текущие Move/Attack/Push
случайности не требуют. RNG fixture проверяет изоляцию и parity случайной дочерней команды.
Это не перенос генерации карт/loot/RNG всей игры в 0.5.

## 7. Урон без фиктивного атакующего

Предлагается `DamageSource : RefCounted`: kind (attack/collision/fall/cell/status),
`source_instance_id`, `origin_cell`, `instigator_unit_id` (может быть UnitId.NONE),
`credit_unit_id` (может быть NONE), root/parent ids. Автор может уже умереть; источник
не требует живого UnitState. Credit — данные для будущих наград, не команда выдачи награды.

`DamageRequest : RefCounted`: target id, amount, damage_type, явный armor_mode (flat/bypass),
source. Amount уже подготовлен источником; attack adapter добавляет STRENGTH один раз,
общий resolver применяет выбранную броню и clamp. Cell/status в будущем передадут свою
величину без атакующего. Impact — отдельный запрос/часть Attack, не скрытое свойство любого урона.
`DamageCommand` и `HealCommand` внутренние; общий путь HP/death/cleanup/reactions используется
атакой, коллизией и будущим окружением. Летальный исход имеет явную причину и тот же cleanup.
Типизированный source заменяет Variant внутри нового API; legacy EventSink адаптируется отдельно.
Тестовый урон с source.kind=cell и NONE автором проверяет шов расширения, не реализует Tile Effects.
Пробивание брони и pipeline FLAT/PERCENT/MULT для урона не проектируются до правил пользователя.

## 8. Минимальный срез и критерии приёмки

Одна небольшая доска, два атакующих участника и третий blocker, одна ближняя атака,
одноклеточный Push, стена/уступ/HAZARD/край; после решений G-1/G-2 — реальные ресурсы.
Одна дефиниция предмета с проверенной runtime-изоляцией на двух владельцах/копиях.
В debug-сцене можно подтвердить отдельные Move и Attack, увидеть preview и журнал исполнения;
ручной допуск через test harness, без Battle Flow и без изменения старого InitiativeTimeline.

Приёмка 0.5: исполнены все три команды и обязательные последствия, однократная смерть,
отказ без мутаций, согласованная экономика, deterministic trace, полное preview по поддержанному
срезу с предметом/RNG/ресурсами, импорт + регрессионные тесты + визуальная проверка этой связки.
Старые 125 passed не являются доказательством этих свойств. Пустой headless startup также недостаточен.
