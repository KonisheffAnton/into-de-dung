## Что признано сильными решениями (НЕ ломать при рефакторинге)

| Решение | Почему сохраняем |
|---|---|
| Отказ от `AStarGrid2D` в пользу своего Dijkstra | Правило высоты — это edge-правило. `AStarGrid2D` умеет запрещать только точки, поэтому `find_path` и `get_reachable_cells` разошлись бы в правилах. Общая `_can_move_between()` гарантирует согласованность. |
| `GridDataProvider` через `Callable` | Честный Dependency Inversion. Именно благодаря нему `GridPathfinder` не придётся менять при вводе `BattleBoard`. |
| Один `DamageInfo` на preview и apply | Исключает расхождение "показали одно, случилось другое". |
| Явные `attacker_cell`/`target_cell` в контракте расчёта | Позволяет превью для Move+Attack комбо ДО фактического перемещения. |
| Y-sort по позиции при `height=0` + отдельный `get_visual_offset()` | Разделяет "логическую глубину" и "визуальный подъём". Без этого высокая клетка перепрыгивала бы порядок сортировки. |
| `StatModifier.source_id` | Позволяет снять все модификаторы источника без ручного отката. |
| Strategy на `Resource` (`TurnOrderStrategy`, `AIBehaviorProfile`, `AIConsideration`) | Data-driven, идиоматично для Godot. |
| Плоский пол в `TILES`, объёмные блоки в `ENTITIES` (`ElevatedTileVisual`) | Единственный способ корректного overlap юнитов и платформ. |

## C — Критические дефекты

### [ ] C-1. Отсутствует сущность `Unit`; `StatsComponent` используется как идентичность юнита
**Симптом.** `DamageInfo.attacker/target`, `AIDecisionContext.enemy_cells`, `InitiativeTimeline._participants`,
`TurnOrderStrategy.compute_order()`, все сигналы `GameEventBus` — типизированы как `StatsComponent`.
«Мешок характеристик» стал первичным ключом личности.

**Последствия.**
- Нет фракции → `enemy_cells`/`ally_cells` приходится заполнять вручную снаружи.
- Нет позиции → её таскают параметром везде (`unit_cell`, `attacker_cell`).
- Нет состояния жив/мёртв, нет `unit_died` → `InitiativeTimeline` не узнает о смерти.
- Нет связи юнит ↔ инвентарь ↔ экипировка (связывается вручную через `@export` в сцене).
- Сериализация невозможна: `StatsComponent : Node`, у юнита нет стабильного id.
- `StatsComponent extends Node` → чистая логика привязана к `SceneTree`, боевой расчёт нельзя выполнить в тесте.

**Решение.** `UnitId` / `Faction` / `UnitState : RefCounted` (id, faction, cell, height, stats, vitals,
inventory, equipment, is_alive, `to_dict`/`from_dict`). `StatsComponent` → `StatsBag : RefCounted`
(+ опциональный адаптер-нода для сцены).

### [ ] C-2. HP/BALANCE хранятся в `Stat.base_value` — порча данных
**Симптом.**
```gdscript
# damage_calculator.gd
hp_stat.set_base_value(hp_stat.get_value() - info.final_damage)
```
`get_value()` = base + модификаторы. Запись результата в `base_value` **впекает модификаторы в базу**.

**Воспроизведение.** HP base=10, амулет +5 → `get_value()=15`. Урон 3 → `set_base_value(12)`,
`get_value()=17`. **HP вырос с 15 до 17 от полученного урона.** Снятие амулета оставляет +2 навсегда.

**Те же места.** `heal_on_damage_effect.gd:20`, `balance_system.gd:33-35`.

**Смежные дефекты.**
- Нет клампа по `HP_MAX` (лечение за максимум, урон в минус).
- Смерть не обрабатывается нигде; нет `unit_died`.
- `HP_MAX` читается ровно в одном месте (`LowHpTargetConsideration`), с `HP` не связан.
- Прямая мутация через публичный `get_stat()` обходит сигнал `stat_changed` → UI не видит урон.
- `GameEventBus.unit_balance_changed` не эмитится нигде (мёртвый сигнал).

**Решение.** Разделить **Attribute** (производное: base+модификаторы — `HP_MAX`, `STRENGTH`,
`IMPACT_POWER`, `MOVE_RANGE`, `INITIATIVE`, `BALANCE_MAX`) и **Vital** (состояние: `hp_current`,
`balance_current` — мутируется, клампится по производному максимуму). Убрать `HP`/`BALANCE` из
`StatTypes`. Ввести `Vitals` с `apply_damage/heal/add_impact` + сигналы `hp_changed/died/balance_broken`.

### [ ] C-3. `TriggeredEffect` хранит per-owner состояние внутри `Resource` — hard error Godot
**Симптом.**
```gdscript
# triggered_effect.gd
var _bound_stats: StatsComponent   # состояние ОДНОГО владельца в РАЗДЕЛЯЕМОМ Resource
func on_equip(owner, stats):
    _bound_stats = stats
    GameEventBus.unit_damaged.connect(_on_unit_damaged)
```
`ResourceLoader` кэширует `.tres` → один экземпляр эффекта на всю игру.

**Воспроизведение.** Дать один предмет двум юнитам:
1. Юнит A: `_bound_stats = A`, connect.
2. Юнит B: `_bound_stats = B` (**перезатёрло A**), повторный connect того же Callable →
   Godot: `Signal 'unit_damaged' is already connected to given callable`.
3. A теряет предмет → `_disconnect_signal()` отписывает всех; у B предмет перестаёт работать.

Плюс `Item.apply_to()` мутирует разделяемый Resource (`effect.item_id = id`).

**Вывод.** Модуль 5 работоспособен только при ровно одном экземпляре предмета в игре. Для роглайка — блокер.

**Решение.** Def/Instance split: `ItemDef`/`ItemEffectDef` (Resource, immutable) →
`ItemInstance`/`ItemEffectRuntime` (RefCounted, per-owner). См. правило R-1 в `DECISIONS.md`.

### [ ] C-4. Нет `BattleBoard` — авторитетного состояния доски
**Последствия.**
- `PushResolver.validate_push()` не знает о юнитах → толкание в занятую клетку «успешно».
  **Push-коллизия (врезался в другого → оба получили урон) — центральная механика жанра — невыразима.**
- `GridPathfinder` не знает о юнитах → `get_reachable_cells` возвращает клетки под врагами →
  AI строит кандидатов на занятые клетки.
- `AIDecisionContext.enemy_cells/ally_cells/hazard_cells` заполняются вручную (нет реестра).
- `GridDataProvider` — хороший DI, но каждый потребитель собирает замыкания сам → неизбежное
  расхождение правил между системами.

**Решение.** `BattleBoard : RefCounted` — единственный источник правды: размер, высоты
(`PackedInt32Array`, не Dictionary), террейн, occupancy (`cell -> UnitId`), hazards, `board_version`,
`make_data_provider(ignore_unit)`, `to_dict/from_dict`.

## S — Нарушения SOLID / расширяемости

### [ ] S-1. `DamageCalculator` закрыт для расширения (OCP)
`info.final_damage = base_damage + attacker_strength` — хардкод. Каждый предмет вида «+50% урона по
цели со сломанным балансом», «игнорировать броню», «крит в спину» требует правки ядра.
`damage_type: StringName` объявлен и **нигде не читается** (мёртвое поле, иллюзия поддержки типов).
Нет резистов/брони. 8 позиционных параметров в `calculate()` — сигнатура не масштабируется.

**Решение.** `DamageContext` + `DamageModifier : Resource` (стадии PRE/FLAT/PERCENT/MULT/POST/CLAMP,
`applies()`/`modify()`) + `DamageResolver`. Новый предмет = новый `.tres` без правки ядра.

### [ ] S-2. `DamageInfo extends Resource` — неверный базовый класс
Транзиентный DTO на один кадр наследует `Resource` (RID, инфраструктура загрузки), причём все поля
через `var`, а не `@export` → всё равно не сериализуется. Взяты только накладные расходы.
Показательно: `AIDecisionContext` в комментарии прямо объясняет, почему он `RefCounted` — правило
знали, но к `DamageInfo` не применили.
Цена: `UtilityAIController` создаёт `DamageInfo` на каждую пару (клетка × враг) — 40×4 = **160
Resource-аллокаций на ход одного юнита**.

### [ ] S-3. Utility AI: расширяемость заявлена, но не обеспечена
- **(а)** `_generate_candidates()` — приватная статическая функция с захардкоженными move /
  move_and_attack. Добавление «способность»/«предмет»/«отступить» = правка контроллера.
  Нужны подключаемые `AIActionGenerator : Resource` в профиле.
- **(б)** `action_type: StringName` (stringly-typed), и **considerations хардкодят эти строки**:
  `if action.action_type != &"move_and_attack"`. Новый тип `&"use_ability"` (тоже наносящий урон)
  будет проигнорирован всеми considerations. Оценивать надо по наличию данных
  (`action.damage_info == null`), а не по типу.
- **(в)** «Нет мнения» реализовано как `return 0.0` при взвешенном среднем → **баг скоринга**.
  В `aggressor_profile` 3 из 4 considerations дают 0 для `move` → любая атака заведомо выше любого
  перемещения, профиль не умеет выбирать позицию. Нужно: `ABSTAIN = NAN` (исключение из знаменателя),
  veto (`-INF`), и геометрическое среднее с компенсацией вместо арифметического.
- **(г)** Недетерминированный тай-брейк: строгий `>` + порядок `reachable_cells.keys()` (порядок
  вставки Dijkstra). Ломает реплеи/сиды и воспроизведение баг-репортов.

### [ ] S-4. `core/**` напрямую зависит от автозагрузок
`DamageCalculator` (static!) эмитит в `GameEventBus`; `InventoryComponent` тоже; `IsoCameraController`
подписывается на `InputManager`. Следствия: логику нельзя протестировать без автозагрузок; нельзя
иметь изолированную симуляцию (нужна для AI-lookahead, реплеев, sandbox-превью).
**Решение.** `EventSink` с инжекцией: в игре — адаптер над `GameEventBus`, в тестах — `RecordingEventSink`,
в lookahead — `NullEventSink`.

### [ ] S-5. `GameEventBus` — будущий god-object и синхронно-реентрантен
К модулю 12 сигналов будет 60+ в одном файле.
**Важнее реентрантность:** в `DamageCalculator.apply()` HP меняется → синхронно эмитится
`unit_damaged` → `HealOnDamageEffect` **уже изменил HP обратно** → и только потом считается баланс.
Порядок «урон → лечение → баланс» получился случайно. Предмет «при получении урона наносит 1 урон
атакующему» + два таких юнита = потенциальная бесконечная рекурсия.
**Решение.** Домены (`CombatEvents`/`MetaEvents`/`UIEvents`); события в очередь вместо синхронных
мутаций (реакция → новый `Command`); лимит глубины цепочек; типизировать `source: Variant`.

## M — Mobile-First UX

### [ ] M-1. Нет контекста ввода (input stack); события нельзя потребить
`debug_grid_visualizer`, `debug_combat_panel`, `debug_ai_panel`, `debug_inventory_panel` —
все подписаны на `InputManager.primary_action`. Один тап дёргает всех, нет флага `handled`.
Блокирует Battle Flow: нельзя запретить ввод во время `ActionExecution`/`EnemyTurn`, нельзя
по-разному трактовать тап в режимах Idle/UnitSelected/Targeting/ConfirmPending.
**Решение.** `InputRouter` со стеком `InputContext`, `handle_*() -> bool` (true = потреблено).

### [ ] M-2. `camera_zoom(factor, center)` — `center` игнорируется
`func _on_camera_zoom(factor: float, _center: Vector2)` — подчёркивание признаёт неиспользование.
Pinch-to-zoom зумит в центр экрана, а не между пальцами; колесо не зумит к курсору.
На мобильном воспринимается как сломанный жест.

### [ ] M-3. Нет границ камеры
Ни `limit_*`, ни клампа по размеру доски. С инерцией на тач-устройстве игрок постоянно улетает в пустоту.

### [ ] M-4. Инерция пана посчитана некорректно
`_on_camera_pan` вызывается из обработки ввода 0..N раз за кадр (при мультитаче — на палец), а внутри
делится на `get_process_delta_time()` → скачки скорости. Нужно аккумулировать дельту за кадр и считать
скорость один раз в `_process`. Плюс `lerp` с фиксированным коэффициентом framerate-dependent
(нужно `1 - exp(-k*dt)`).

### [ ] M-5. Требование «Mouse/**Keyboard**» не выполнено
В `project.godot` **нет секции `[input]`** — `InputMap` пуст. Нет WASD/стрелок, `ui_cancel` (Esc —
обязателен для отмены таргетинга), `ui_accept`, Tab (следующий юнит), горячих клавиш, геймпада.
Клавиатура обязана идти через `InputMap`, иначе ремап невозможен.

### [ ] M-6. Hover как основа превью — PC-only тупик
`pointer_moved` на touch не эмитится (задокументировано), но превью строится на hover → на мобильном
превью не существует. Требование «обязательный предпросмотр» требует явной модели:
tap = выбрать → показать превью → Confirm = выполнить. Нужны `SelectionState`/`TargetingState`.

### [ ] M-7. `project.godot` не подготовлен к мобилке
Отсутствуют: `window/size/viewport_width/height` (вообще не заданы),
`window/handheld/orientation`, **`input_devices/pointing/emulate_touch_from_mouse=true`**
(критично для отладки тача на PC).
`rendering_device/driver.windows="d3d12"` при `rendering_method="gl_compatibility"` — противоречиво.
**Safe area нигде не используется** (`DisplayServer.get_display_safe_area()` — 0 упоминаний) при
заявленном «Mobile-first UX + safe areas».
Нет константы минимального тач-таргета (~48dp) и DPI-нормализации: `tap_max_distance = 16.0` в
пикселях = разное физическое расстояние на телефоне и 4K-мониторе. Пороги жестов должны быть в
физических единицах через `DisplayServer.screen_get_dpi()`.

## D — Дефекты по модулям

### Модуль 1 — Grid / Input
- [ ] **D-1.1** Нет `grid_size` в `IsoGridConfig` → границы дублируются в `GridPathfinder.configure(bounds)`,
  `debug_ai_panel` (`grid_width/height`), визуализаторе. Нарушение SSOT.
- [ ] **D-1.2** `resolve_grid_with_height()` — эвристика, которая будет ошибаться: итерация может
  зациклиться A→B→A и выйти по `max_iterations`, вернув неверную клетку. Корректно — перебор
  высот сверху вниз: для каждого `h` от максимальной к 0 взять `screen_to_grid_flat(pos, h)` и
  вернуть первую клетку, чья реальная высота равна `h`. Детерминированно.
- [ ] **D-1.3** `screen_to_grid_flat` молча возвращает `Vector2i.ZERO` при `tile_size == 0` —
  маскирует ошибку конфигурации вместо `assert`. Нет проверки границ.

### Модуль 2 — Rendering
- [ ] **D-2.1** Магический сдвиг `-1.0` по Y в `ElevatedTileVisual` для разрешения равного ключа
  сортировки — хрупко. Нужен явный `sort_bias: float` в `YSortable` + задокументированная шкала.
- [ ] **D-2.2** Многотайловые объекты (2×2 укрытия — упомянуты в комментарии `YSortable`)
  **математически не сортируются по одному якорю**: объект должен быть одновременно «перед» одним
  юнитом и «за» другим. Признать ограничение и выбрать стратегию (разбиение спрайта по клеткам /
  топологическая сортировка) ДО появления арта.
- [ ] **D-2.3** Отрисовка сетки через `_draw()` не масштабируется. Продакшену нужен `TileMapLayer`
  (по слою на высоту) или `MultiMeshInstance2D`. На мобилке — разница между 1 и сотнями draw-call.

### Модуль 3 — Pathfinding
- [ ] **D-3.1** `frontier.sort_custom()` **внутри `while`** → фактическая сложность O(n² log n),
  а не заявленная O(n log n). На 16×16 = ~десятки тысяч сравнений с лямбдой, а
  `get_reachable_cells` вызывается на каждое решение AI и на каждое движение мыши при превью.
  Нужен бинарный min-heap или bucket-queue (стоимости целочисленные и малые).
- [ ] **D-3.2** `is_cell_reachable()` делает полный flood-fill и выбрасывает результат.
- [ ] **D-3.3** Нет кэша `reachable` по `(unit, board_version)`.
- [ ] **D-3.4** `frontier: Array` с вложенными `Array` — нетипизировано, аллокация на вставку.
  Противоречит правилу strict typing.
- [ ] **D-3.5** `came_from[walk_cell]` без проверки ключа → потенциальный краш при рассинхроне.
- [ ] **D-3.6** Нет `ignore_unit` (юнит блокирует сам себя) — следствие C-4.

### Модуль 4 — Stats / Initiative
- [ ] **D-4.1** `ADD_PERCENT` считается от `base_value`, а `MULTIPLY` — от накопленного результата.
  Смешивать их в списке, отсортированном по `priority`, семантически неопределённо. Комментарий
  описывает соглашение, которое код не обеспечивает. Нужен фиксированный конвейер:
  `(base + Σflat) * (1 + Σpercent) * ∏mult` → `priority` становится не нужен, результат не зависит
  от порядка добавления (важно для сохранений).
- [ ] **D-4.2** `_recompute_value()` делает `duplicate()` + `sort_custom()` с лямбдой при каждом
  пересчёте; любое надевание предмета инвалидирует статы. Фиксированный конвейер убирает и то, и то.
- [ ] **D-4.3** Нет клампов/границ стата. `HP_MAX = 0` молча ломает `BalanceSystem.would_break`
  (всегда false) и `LowHpTargetConsideration` (всегда 0). Нужен `StatDef` (min/max/default).
- [ ] **D-4.4** `_get_or_create_stat` молча создаёт стат = `0.0`. Опечатка в типе → тихий ноль вместо
  ошибки. Нужна схема статов юнита (`UnitStatsProfile`) + `assert` в debug.
- [ ] **D-4.5** `StatTypes` как `enum` небезопасен для сохранений: вставка значения в середину
  сдвигает индексы и ломает старые save-файлы и `.tres`. Либо `StringName` + реестр `StatDef`,
  либо жёсткое правило «только append». (См. R-4 в DECISIONS.md.)
- [ ] **D-4.6** **`advance_turn()` + `unregister_participant()` = баг при смерти.**
  `unregister_participant` → `recompute_order()` → **`_current_index = -1`** → смерть посреди раунда
  **перезапускает раунд**, все уже ходившие получат ход снова. Нужен курсор по стабильному `UnitId`
  и разделение «перестроить порядок» vs «удалить участника».
- [ ] **D-4.7** Нет `round_started`/`round_ended`. `%`-обёртка молча начинает новый раунд.
  **Без этого модуль 9 (tick-based статусы) нереализуем.**
- [ ] **D-4.8** `compute_order(Array) -> Array` — модель «отсортированный список», которая **не
  выражает** time-based timeline (ATB/CTB, юнит с двумя ходами за раунд), хотя требование называется

### Модуль 6 — Combat
- [ ] **D-6.1** `PushResolver.validate_push()` возвращает нетипизированный `Dictionary` с магическими

## Итог

Каркас написан аккуратно, местами очень грамотно (см. таблицу сильных решений). Но есть:
1. **одна корневая ошибка моделирования** — отсутствие сущности `Unit` (C-1);
2. **три реальных дефекта** — порча `base_value` (C-2), per-owner состояние в `Resource` (C-3,
   hard error на втором экземпляре предмета), отсутствие occupancy (C-4, делает невыразимой
   главную механику жанра);
3. **системный разрыв** — расширяемость AI и урона заявлена в документах, но не обеспечена кодом
   (S-1, S-3);
4. **неверный порядок модулей** — Command/Queue обязан идти до Battle Flow (G-4).

**Решение: рефакторить, не переписывать.** Все дефекты имеют природу «не хватает слоя», а не
«сделано неверно». Чистая логика (координаты, Dijkstra, статы, push-геометрия, скоринг) в основном
корректна и не зависит от владельца состояния — именно потому, что была сделана stateless/static.
~60% файлов остаются практически неизменными; реальный рерайт — только модуль 5 и `DamageCalculator`.
