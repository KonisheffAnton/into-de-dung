## 2. Расчёт одного типа и предложения о входных данных

Обозначения: D — урон после подготовки источника, до защиты; A — броня до
попадания; rA — сопротивление от брони, rH — естественное сопротивление этому
типу. rA/rH — набранные значения до лимитов. Броневая ветвь использует их сумму,
прямая HP-ветвь — только rH. U, ответ 2026-09-20: лимит применяется к итоговой
защите каждой ветви, а не к составляющим перед сложением. Стандартный лимит 75%.
Перки могут поднять допустимое сопротивление выше 100%; глобального cap=100% нет.

L_B/L_H — допустимые пределы для типа в броневой/HP-ветви с учётом разрешённых
перками повышений/превышений; по умолчанию оба равны 0.75. В числовых примерах
изменённый предел задаётся явно. U, следующее уточнение: допустимый максимум
определяется только перками; отдельного абсолютного потолка поверх L_B/L_H нет.
Конкретные перки, правила их сложения и возможность менять пределы ветвей
независимо ещё не выбраны. Повышенный предел сам по себе не добавляет сопротивление:
эффективная защита всё ещё ограничена набранным значением.
Эффективные сопротивления: R_B=min(rA+rH,L_B), R_H=min(rH,L_H).
Например, rA=80%, rH=40%, обычные лимиты → R_B=75%, R_H=40%.
При разрешённом пределе L_B=110% та же сумма даёт R_B=110%.
Это обозначения проекта расчёта, не существующие поля/API. U, ответ 2026-09-20:
отрицательные rA/rH допустимы как уязвимость (§2.3); отсечения на нуле нет.
U, следующее уточнение: нижней границы сопротивлений нет. Особые обходы ещё открыты.

U/Q4: броневая ветвь проходит сумму защит, прямая HP-ветвь — естественную защиту,
в обоих случаях с применимым лимитом. Непоглощённый повреждающий остаток уже прошёл
защиту и повторно не уменьшается. Для случая R_B<=1 и R_H<=1, без лечения:

```text
H0 = D * p                    B0 = D - H0
B1 = B0 * (1 - R_B)
C  = min(A, B1)               O = B1 - C
H_direct = H0 * (1 - R_H)     H1 = H_direct + O
A_after = A - C               hp_dealt = min(HP_before, H1)
```

При отсутствии/нулевом остатке брони B0=0: сопротивление от брони ничего не гасит.
rA не применяется к прямой HP-ветви. Естественная защита действует один раз на каждую исходную
ветвь; при переходе O в здоровье защиты уже учтены. Сумма сопротивлений на B0
не заменяется последовательным умножением (1-rA)*(1-rH).

Эталон последнего ответа: HP=100, D=200, A=50/100, p=0, rA=20%, rH=30%:
общая защита 50% оставляет B1=100; C=50 уничтожает броню, O=50 снимает HP.
Итог A=0, HP=50. Повторные 30% дали бы 35 HP-урона и HP=65 — это не принято.
Прежний эталон D=200, A=60/100, rA=50%, rH=25% теперь даёт 50 A/0 HP:
сумма 75% оставляет 50 урона, который полностью поглощает броня.
Старое значение 60 A/30 HP относится к заменённой редакции, не текущей приёмке.

U/Q5: целые D/HP/броня. U, ответ 2026-09-20: после всех применимых модификаторов
подготовки урона один `floor` по объединённому типу/политике даёт D. До этой
границы дроби сохраняются; промежуточные операции и отдельные предметы не округляются.
Это округление входа не заменяет округления ветвей после разделения и защиты.
Для обычного урона: H0=floor(D*p), B0=D-H0;
B1=floor(B0*(1-R_B)); C=min(A,B1);
O=B1-C; H_direct=floor(H0*(1-R_H)); H1=H_direct+O.
Потери от сопротивлений не возвращаются
в другую ветвь. Нет принудительного минимума 1 после защиты. Дробные значения
старых профилей D1 сохраняются; переход существующих float-ресурсов в D2 требует
отдельной миграции, а не тихого округления при загрузке.

Примеры подготовки входа (U, арифметика проекта):

| Подготовка урона одного типа/политики | Значение до floor | Целый D |
|---|---|---|
| База 3, высота ×1.5, стойка ×0.7 | 3.15 | 3 |
| База 1, стойка ×0.7 | 0.7 | 0 |
| Два компонента по 0.6 после применимых модификаторов | 1.2 | 1 |

В первом примере промежуточное округление после высоты ошибочно дало бы D=2.
В последнем округление отдельных источников ошибочно дало бы D=0.
Вариант дробных ресурсов с округлением только в UI не выбран. Порядок и область
будущих модификаторов не задаются одним правилом округления. Распределение нехватки
брони между повреждающими типами принято в §4; единый итог HP смешанного попадания
принят в §2.2, допуск состояния — в §5; форма событий ещё уточняется.

### 2.1. Превышение 100%: восстановление HP

U, ответ 2026-09-20: при эффективном сопротивлении выше 100% соответствующая
ветвь восстанавливает HP; для броневой ветви это тоже HP, а не ремонт брони.
Пример пользователя: 10 единиц огня при эффективных 110% дают 1 HP лечения.
Речь об эффективном сопротивлении с разрешённым перками превышением, а не о
набранных 110% при неизменённом стандартном лимите 75%.

Вещественная величина восстановления для ветви X и её эффективного R>1:
G=X*(R-1). Ветвь при этом не расходует броню/HP, а восстановление не проходит
сопротивления повторно. Для R=1 ветвь полностью блокируется без восстановления.
U, ответ 2026-09-20: целое восстановление G_int=floor(X*(R-1)) при R>1;
округляется положительная величина каждой ветви, без обязательного минимума 1 HP.
Внутри попадания положительный урон и восстановление требуют раздельного учёта;
отрицательный B1 нельзя использовать как расход/распределение запаса брони.

| Ветвь, уже выделенная из попадания | Эффективная защита | Результат при достаточном недостающем HP |
|---|---|---|
| Прямая HP-ветвь: 10 огня | R_H=110%, предел разрешает | +1 HP |
| Броневая ветвь: 10 огня | R_B=110%, предел разрешает | +1 HP, без ремонта/расхода брони этой ветвью |
| Прямая HP-ветвь: 3 огня | R_H=110%, предел разрешает | floor(0.3)=0 HP |
| Прямая HP-ветвь: 19 огня | R_H=110%, предел разрешает | floor(1.9)=1 HP |
| Броневая и прямая HP-ветви по 6 огня | R_B=R_H=110%, пределы разрешают | floor(0.6)+floor(0.6)=0 HP |
| Прямая HP-ветвь: 20 огня | rH=300%, L_H=250% → R_H=250% | +30 HP |
| Прямая HP-ветвь: 20 огня | rH=120%, L_H=250% → R_H=120% | +4 HP |
| Прямая HP-ветвь: 20 огня | rH=300%, L_H=150% → R_H=150% | +10 HP |

Пределы 150%/250% — условия примеров набранных перков, не готовые перки.
Другого потолка поверх разрешённого перками нет; набранные 300% при обычном
лимите 75% по-прежнему дают R_H=75%, а не лечение.

Округление выполняется после объединения источников одного типа/политики и
разделения на ветви; дроби восстановления разных ветвей перед floor не складываются.
Floor отрицательного числа не используется: floor(-0.3)=-1 дал бы 1 HP лечения,
тогда как принятый floor положительной величины 0.3 даёт 0.
Единый итог HP, ограничение HPmax и смерть согласованы в §2.2, допуск состояния —
в §5. Форма событий для смешанного результата ещё открыта.

### 2.2. Единый итог HP одного попадания

U, ответ 2026-09-20: весь HP-урон и восстановление одного попадания сначала
суммируются, затем здоровье меняется один раз с ограничением 0..HPmax.
Смерть проверяется по итоговому HP; временной смерти между компонентами нет.
Для живой цели с корректным 0<HP_before<=HPmax:

```text
T_damage = sum(прямой HP-урон + непоглощённый повреждающий остаток брони)
T_heal = sum(целое восстановление HP от обеих ветвей каждого типа)
HP_after = clamp(HP_before - T_damage + T_heal, 0, HPmax)
```

В T_damage/T_heal уже учтены модификаторы, защиты и округления каждой ветви.
Повреждающие суммы не ограничиваются текущим HP до сложения с лечением;
восстановление не ограничивается недостающим HP до этого сложения.
Порядок типов/источников не влияет на итог. Избыток лечения сверх HPmax не
создаёт сверхмаксимального здоровья. Это правило одного попадания по живой цели,
оно не разрешает лечение уже мёртвой цели как неявное воскрешение.

| HP до / max | T_damage | T_heal | HP после | Результат |
|---|---|---|---|---|
| 8 / 100 | 10 | 6 | 4 | Цель жива; пример пользователя |
| 8 / 100 | 10 | 10 | 8 | HP не изменились |
| 8 / 100 | 20 | 6 | 0 | Смерть по итоговому HP |
| 8 / 100 | 10 | 2 | 0 | Ровно нулевой итог, смерть |
| 95 / 100 | 10 | 20 | 100 | Единственное ограничение после суммирования |
| 5 / 10 | 0 | 20 | 10 | Чистое лечение ограничено HPmax |
| 8 / 100 | 10 | 0 | 0 | Чистый смертельный урон |
| 8 / 100 | 0 | 0 | 8 | Нулевой результат |
| 8 / 100 | 10 | 16 | 14 | Лечение превышает повреждение |

В первом примере преждевременный overkill-clamp до 8 превратил бы итог в 6 HP
вместо принятых 4. При 95/100 применение лечения первым с ранним HPmax-clamp
дало бы 90 HP вместо принятых 100. Ни один из этих промежуточных clamp не применяется.
Лечение отдельной последующей реакцией не включается в T_heal уже завершённого
попадания. Итоговая разница HP не заменяет повреждающую часть для U2 (§5).
Количество/поля событий для смешанного попадания ещё открыты.
Один итог HP не означает транзакционный откат всей цепочки A/HP/движения;
guarded-мутации и сохранение фактического prefix остаются требованиями D2.

30/10, V=3 → доли 2.25/0.75 → после floor 2/0 → оставшаяся единица шлему → 2/1.

по постоянному порядку, даже если входной список перечисляет их в обратном порядке.

U/Q6, уточнение 2026-09-21: избыток восстановления не теряется сразу, а сохраняется
как броня сверх обычного максимума. После боя оставшийся избыток исчезает,
если в перке не указано другое. Для успешного восстановления в бою добавляемый избыток равен
E_added=max(0,V-M); Amax от него не увеличивается. Это обозначение величины,
не выбранная схема хранения или отдельная характеристика прочности.

Пример без дальнейшего расхода брони и без меняющего правило перка:
35/40 + восстановление 20 → обычный запас 40 и временный избыток 15,
всего 55/40 → после боя 40/40. По принятой формуле p при 55/40 равна 0.
Исчезновение избытка не восстанавливает повреждённый обычный запас предметов.

U/Q6, следующий ответ 2026-09-21: в бою заклинание восстановления брони можно
применить при полностью восстановленном обычном запасе. При M=0 обычное
восстановление W=0; доли q_i не вычисляются, деления на M нет. Весь объём V
становится временным избытком и подчиняется уже принятым правилам его расхода/срока.
Пример без прежнего избытка: 40/40 + V=20 → 60/40, из них 20 временных;
без дальнейшего расхода/восстановления и особого перка после боя остаётся 40/40.
Случай Amax=0 остаётся открытым.

U/Q6, следующий ответ 2026-09-21: создавать временный избыток заклинаниями вне
боя пока нельзя. Возможность отложена для будущего обсуждения; это не разрешение
её реализовать. Обычное восстановление брони вне боя этим ответом не отменяется.
Исход/стоимость внебоевого применения с объёмом больше недостачи ещё не выбраны;
новый избыток от него сейчас не появляется. Правило перка о сроке уже имеющегося
избытка сохраняется и само по себе не разрешает создавать новый вне боя.

U/Q6, следующий ответ 2026-09-21: избыток от повторных применений складывается
с уже оставшимся избытком; верхнего предела накопления нет.
E_after=E_before+E_added, где E_before — остаток к моменту нового восстановления.
Новое применение не заменяет прежний остаток и не ограничивает его величиной Amax.
Обычный максимум Amax остаётся прежним. Пример последовательных применений в бою,
без расхода между ними, каждое по 20:

| До применения | Добавленный временный избыток | После применения | Всего временного избытка |
|---|---|---|---|
| 40/40 | 20 | 60/40 | 20 |
| 60/40 | 20 | 80/40 | 40 |
| 80/40 | 20 | 100/40 | 60 |

Если после расхода осталось 5 временных единиц, новое применение на 20
даёт 25 временных единиц при полном обычном запасе.
Весь оставшийся временный избыток по-прежнему исчезает после боя, если перк
не задаёт другое правило; сложение не восстанавливает уже израсходованный избыток.

U/Q6, следующий ответ 2026-09-21: временный избыток расходуется первым,
затем расходуется обычная броня предметов по случайному правилу §4.1.
Из общего расхода C_total уже после защит и распределения между типами
избыток принимает C_temp=min(E_before,C_total); предметы принимают остаток.
Это порядок списания рассчитанных единиц брони, а не дополнительная защита
или отдельное попадание. Доля p остаётся взятой до всего попадания.

Примеры: обычная броня 40/40, временный избыток 15, всего 55/40;
после указанного расхода больше нет попаданий/восстановления или особого перка.

| Общий расход брони | Из временного избытка | Из предметов | Сразу после расхода | После боя |
|---|---|---|---|---|
| 10 | 10 | 0 | 45/40 (40 обычных + 5 временных) | 40/40 |
| 15 | 15 | 0 | 40/40 | 40/40 |
| 18 | 15 | 3 | 37/40 | 37/40 |

Пропорция восстановления не меняет случайный расход
брони по предметам при попадании (§4.1). Это отдельный эффект восстановления
брони; лечение HP от сопротивления выше 100% по-прежнему не ремонтирует броню.
Открыты: конкретный стабильный ключ предметов, подготовка целого объёма V
из параметров заклинания; технический учёт/принадлежность избытка,
взаимодействие с Amax=0; конкретные исключения перков и обработка превышения
недостачи при восстановлении вне боя. Создание избытка вне боя отложено, сейчас не разрешено.
Применение в бою при полном обычном запасе принято; стоимость успешного заклинания
при малой/нулевой недостаче, параметры заклинаний и правила ремонта ещё открыты.
Принятое правило обычного заклинания не определяет распределение ресурсного ремонта.

Числа для стойки (U, D=20, A=25/100): до разделения D=14 → ΔA=7, ΔHP=7.
Альтернатива «уменьшать только HP после защиты» дала бы ΔA=10, ΔHP=7 и не выбрана.
При исходном уроне 1 стойка даёт 0.7, принятый floor даёт D=0: броня и HP
не теряются; воздействие на равновесие остаётся отдельным каналом.
Падение (P): HPmax=100, forced drop_steps=4 → база 50. При A=25/100
получаем 25 A/25 HP. Нынешняя формула с числовым ARMOR=25 дала бы 25 HP
без расхода брони; совпадение HP в примере не означает прежнюю механику.

U2, уточнение 2026-09-20: для допуска состояния сохраняется положительная
повреждающая HP-часть после защит/округления, до взаимозачёта с лечением.
Не проверять этот допуск по итоговой разнице HP. Принятый пример: цель без
действующей брони, 50/100 HP; меч даёт 10 физического урона при нулевой физической
защите и 100 огня при эффективной огненной защите 110%. Физическая часть даёт
10 HP-урона, огонь — 10 HP лечения; итог остаётся 50 HP, кровотечение от
физической части накладывается. Лечение внутри попадания не отменяет её допуск.
Тот же принцип сохраняет допуск при положительном итоговом восстановлении HP.

Примеры для кровотечения, связанного с физической частью; все значения ниже
уже после защит/округления, цель жива, иных запретов на состояние нет:

| HP до / max | Физическая HP-часть | Лечение от огня | Потеря брони | HP после | Условие HP-урона для кровотечения |
|---|---|---|---|---|---|
| 50 / 100 | 10 | 10 | 0 | 50 | Да |
| 50 / 100 | 10 | 20 | 0 | 60 | Да |
| 50 / 100 | 10 | 6 | 0 | 46 | Да |
| 50 / 100 | 0 | 10 | 0 | 60 | Нет |
| 50 / 100 | 0 | 0 | 10 | 50 | Нет |
| 50 / 100 | 1 | 1 | 0 | 50 | Да |

Чистое лечение, полностью защищённая/округлённая до нуля HP-часть и только
потеря брони не выполняют это условие. Лечение отдельной последующей реакцией
тоже не отменяет уже нанесённый урон. Обход условия не отменяет иммунитет автоматически.
Привязка других конкретных состояний к типу/части/источнику описывается в D3;
положительная часть чужого попадания или последующего collision не подменяет нужную.
Нынешние `hp_dealt`/`damaged` описывают фактическое изменение HP по прежнему коду;
их смысл не переименовывается молча в повреждающую составляющую нового попадания.
Для D2 нужно отдельно сохранить повреждающие части и итоговую разницу HP в
объяснении/результате; формат событий и условия реакций предметов ещё не выбраны.
P: состояние на погибшую цель не накладывается; имеющиеся состояния не снимаются
из-за нового запрета. Нельзя разрешать состояние прямой атаки по HP-урону её
последующего столкновения. Дым/DoT/перки требуют собственной политики в D3/D5.

Collision выполняет target и blocker последовательно **внутри одного шага**.
Между ними возможны синхронные сигналы/checkpoints, но игровые реакции очереди
не исполняются. ActionQueue собирает item reactions по damaged, выполняет
mandatory-поддерево прежде этих реакций; смерть/occupancy оформляются HP-путём.
Новый расход брони требует собственного объяснения/события: при ΔHP=0 старый
damaged не возникает. Не запускать существующее лечение «при HP-уроне» от ΔA.

DamageSource уже допускает kind status/item/cell, но это форма происхождения,
не реализованные DoT/огонь/атакующий предмет. Нынешние item reactions лечат;
новые повреждающие реакции должны создавать команды, а не вызывать Vitals напрямую.
Для будущих статусов/клеток нужен явный выбор защиты и условия наложения, без
фиктивного атакующего. Restore/from_dict, set_hp, revive и heal — не попадания.
Прямой legacy heal при over-max HP может уменьшить HP; ActionHpExecutor.heal
имеет защиту от этого. Это не обход урона, которым можно пользоваться в новом бою.

## 7. API и граница D1 / D2

Существуют: `AttackDefinition(id, profile)` (поля Resource),
`AttackCommand(actor_unit_id, target_unit_id, expected_actor_cell, expected_target_cell,
attack_definition_id, expected_revision)`, `DamageRequest(target_unit_id, amount,
damage_type, armor_mode, source)`, `DamageSource(kind, source_instance_id,
origin_cell, instigator_unit_id, credit_unit_id)`, `ActionHpExecutor.damage`/
`damage_spatial`, `Vitals.apply_damage`/`apply_spatial_damage`,
`BalancePushRules.prepare_attack(...raw_attack, hit_amount, main_after, spatial)`.
`ActionQueue.submit(command, context)` и `AttackForecast.build(context, queue,
command)` остаются владельцами исполнения и изолированного прогноза.

P/D1, только после поручения на код:

1. Извлечь нынешнюю формулу прямого удара из AttackCommand._prepare в чистый
   расчёт проверенных чисел. Предлагаемые входы: strength, weapon, armor,
   height multiplier/profile, guard; выходы: raw_attack, scaled, hit_amount,
   структурированное объяснение стадий. **Это описание будущего API, не класс в коде.**
2. AttackCommand сохраняет validate/preflight, оплату, источники, sealed request
   и передачу прежних raw_attack/hit_amount в BalancePushRules. Не переносить
   collision-базу в модифицированный прямой урон. В этой минимальной версии не
   нужны новые типы, поля AttackDefinition, snapshot schema или модификаторы.
3. Legacy DamageCalculator и прямой flat/bypass, balance/spatial/fall/death
   остаются побайтово прежними по результатам; новый helper не унифицирует их
   разные минимумы. Receipt/revision/RNG/counters/FAULTED prefix не меняются.
4. Новое объяснение не меняет frozen receipts; способ передачи в UI уточнить
   в пакете D1, не добавлять формулу в UI. Нынешний forecast исполняет тот же код.

P/D2, отдельная более широкая граница: runtime Acurr и capability отдельно от
производного Amax; две карты сопротивлений и допустимые пределы от перков;
учёт временного избытка и его срока с исключениями перков после согласования
открытых правил §4.2; эти данные тоже потребуют изоляции/сохранения в прогнозе;
типизированное описание попадания и
результата с provenance; единый владелец защиты и guarded мутации A/HP. Старый
ARMOR не переименовывается молча в Acurr/Amax. Новые данные добавляются вместе с
проверкой, copy/restore/миграцией Unit/Simulation/ItemSimulation snapshots и
объяснением forecast. Диапазоны stat ID проверяются в нескольких владельцах.
Превращение урона в восстановление HP требует явного результата лечения и его
согласованного исполнения; отрицательные суммы нельзя передавать в нынешние
damage-запросы или трактовать как отрицательный расход брони. Принят единый итог HP
по §2.2 и допуск состояния по повреждающей HP-части до лечения (§5).
Форма событий и условия реакций предметов смешанного попадания ещё открыты;
нельзя подменить часть урона для U2 итоговой потерей HP или наоборот.
Это проект нового пути с одной итоговой записью HP, не готовый API.

Обязателен preflight новых ресурсов и checkpoints после каждой записи/сигнала;
admission рассчитывает смерть/board touches по HP после защиты и будущей броне
цепи. Текущие seals включают amount>=1 и bypass — их нельзя считать готовыми для
нового нулевого HP-урона. Лимит очереди/fault сохраняет уже записанный A/HP-prefix,
не полную отмену. Форму события брони, последовательность записей A/HP, schema
versions и миграцию надо закрепить отдельным техническим пакетом D2; frozen
P02–P08/§4.5 не редактировать. Старые профили остаются явно legacy и не принимают

## 8. Проверки и оставшиеся решения

D0 проверяется чтением кода, арифметикой таблиц, ссылками, diff и независимым
обзором проекта. Godot не требуется: исполняемые файлы не меняются.
D1: differential старых трёх профилей и legacy API; armor/guard/height/minimum,
impact/collision/fall, отказы без мутации, лимиты/fault-prefix, resources,
snapshots/receipt/RNG/counters и повторный изолированный forecast.
D2: строки §2.1–§6, отрицательные сопротивления и их компенсация только в нужной
ветви, усиленный остаток без повторной уязвимости, предел 75%/повышенные пределы,
100%/110%, восстановление HP
от обеих ветвей, единый итог смешанного повреждения/лечения, U2 при нулевом/лечащем
итоге HP и положительной нужной повреждающей части, смерть только по итогу,
единственный HPmax/zero-clamp, отсутствие раннего overkill-clamp;
перестановки компонентов/источников, два попадания/два типа,
armor-only hit, полная rH, лечение реакцией, lethal/overkill, независимость impact,
цепь collision→fall, hostile callbacks после записи A/HP, snapshots round-trip,
отказ неизвестных схем/типов и неподдержанного legacy пути, отсутствие live-мутаций.
По [TESTING](TESTING.md): import/startup, адресные тесты, затем
`python tools/demo/isolate.py --check --full` и
`python tools/demo/isolate.py --render-check`; UI настоящим input/scrolling в
отдельном SubViewport. Потом независимое ревью фиксированного кода и commit.

Перед принятием D0 целиком: конкретные перки и правила сложения повышений пределов,
события/реакции смешанного повреждения/лечения
и детализация баз последствий. Единый итог HP, HPmax-clamp и смерть по нему приняты;
допуск состояния по повреждающей HP-части до взаимозачёта с лечением принят.
Отрицательные сопротивления приняты как уязвимость без нижнего предела.
Объединение одинакового типа/политики до округления и отдельные защиты каждого
типа приняты; floor положительной величины лечения каждой ветви без минимума 1,
один floor входа после модификаторов и пропорциональное распределение
брони между повреждающими типами приняты. Принят базовый предел 75% для итоговой
защиты каждой ветви с повышением перками и возможностью превысить 100% ради лечения
HP от обеих ветвей; прежний безусловный cap=100% заменён. Реестр типов не выбран.
Допустимый максимум задают только перки, отдельного абсолютного потолка нет.
Q1–Q5 отвечены в пределах §1–§2; стойка бережёт A/HP;
воздействие на равновесие без HP-урона и отдельные попадания collision/fall приняты.
U/Q6: снятие и замена брони разрешены только вне боя. Повреждения сохраняются
между боями; само завершение боя броню не восстанавливает. Приняты два способа:
восстанавливающие броню заклинания, в том числе в бою, и ремонт на экране персонажей
между уровнями. Запрет смены экипировки в бою не запрещает восстановление заклинанием.
Пример: оставшиеся 30/100 сохраняются к следующему бою при той же экипировке/max
и без ремонта или восстанавливающих броню заклинаний. Остатки брони по экземплярам
сохраняются при переодевании, общие суммы учитывают надетые предметы (§4.1).
Обычное заклинание распределяет восстановление пропорционально недостающей броне
надетых предметов (§4.2); floor и выдача оставшихся единиц по наибольшим дробным
частям с постоянным порядком при равенстве приняты. Избыток сохраняется до конца боя,
если перк не задаёт другое правило; расходуется первым, затем обычный запас предметов.
Учёт/принадлежность и остальные открытые детали избытка — §4.2.
Заклинание в бою при полностью восстановленной броне разрешено; весь объём
становится временным избытком, обычные доли при нулевой недостаче не вычисляются.
Избыток от повторных применений складывается без верхнего предела накопления.
Вне боя новый избыток пока не создаётся; возможность отложена для будущего обсуждения.
Остаток Q6 — влияние других источников на max, технические детали случайного расхода,
конкретный ресурс/цена/объём ремонта и параметры заклинаний. Требование ресурса для
ремонта между уровнями принято; конкретный ресурс и его стоимость ещё не выбраны.
Восстановление брони заклинанием — отдельный эффект; ранее принятое лечение от
сопротивления выше 100% по-прежнему направляется в HP, включая броневую ветвь.
Для D2 требуются соблюдение запрета снятия/замены в бою и начальная миграция;
изменение max от других источников ещё не согласовано. Хаб/межбойное восстановление
не придумывать ради D1. Статусы/иммунитеты/сроки —
D3, среда — D5. Q1–Q5 повторно не спрашивать. Следующее действие — обсудить этот
проект; его наличие не разрешает D1/D2. Плейтест открыт, графика отложена.
