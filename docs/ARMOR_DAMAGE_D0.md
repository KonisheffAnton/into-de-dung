## 2. Расчёт одного типа и входные данные

Обозначения: D — урон после подготовки источника, до защиты; A — броня до
попадания; rA — сопротивление от брони, rH — естественное сопротивление этому
типу. rA/rH — набранные значения до лимитов. Броневая ветвь использует их сумму,
прямая HP-ветвь — только rH. U, ответ 2026-09-20: лимит применяется к итоговой
защите каждой ветви, а не к составляющим перед сложением. Стандартный лимит 75%.
Перки могут поднять допустимое сопротивление выше 100%; глобального cap=100% нет.

U/Q6, следующий ответ 2026-09-21: p выбирается до всего попадания:
при Amax>0 — прежняя clamp(1-2*Acurr/Amax,0,1), при Amax=0 и E_before>0 — 0,
при Amax=0 и E_before=0 — 1. E_before — временная броня до попадания.
При Amax=0 деление не выполняется; последующие компоненты не пересчитывают p.

L_B/L_H — допустимые пределы для типа в броневой/HP-ветви с учётом разрешённых
перками повышений/превышений; по умолчанию оба равны 0.75. В числовых примерах
изменённый предел задаётся явно. U, следующее уточнение: допустимый максимум
определяется только перками; отдельного абсолютного потолка поверх L_B/L_H нет.
A: прибавки перков к лимитам складываются по типу/ветви; правила и эталоны — §9.2. Повышенный предел сам по себе не добавляет сопротивление:
эффективная защита всё ещё ограничена набранным значением.
Эффективные сопротивления: R_B=min(rA+rH,L_B), R_H=min(rH,L_H).
Например, rA=80%, rH=40%, обычные лимиты → R_B=75%, R_H=40%.
При разрешённом пределе L_B=110% та же сумма даёт R_B=110%.
Это обозначения проекта расчёта, не существующие поля/API. U, ответ 2026-09-20:
отрицательные rA/rH допустимы как уязвимость (§2.3); отсечения на нуле нет.
U, следующее уточнение: нижней границы сопротивлений нет. Явные политики обхода определены в §9.1.

U/Q4: броневая ветвь проходит сумму защит, прямая HP-ветвь — естественную защиту,
в обоих случаях с применимым лимитом. Непоглощённый повреждающий остаток уже прошёл
защиту и повторно не уменьшается. Для случая R_B<=1 и R_H<=1, без лечения:

```text
H0 = D * p                    B0 = D - H0
B1 = B0 * (1 - R_B)
C  = min(A, B1)               O = B1 - C
H_direct = H0 * (1 - R_H)     H1 = H_direct + O
A_after = A - C               hp_dealt = min(HP_before, H1)
```

При нулевом общем запасе брони, включая временный, B0=0:
сопротивление от брони ничего не гасит.
rA не применяется к прямой HP-ветви. Естественная защита действует один раз на каждую исходную
ветвь; при переходе O в здоровье защиты уже учтены. Сумма сопротивлений на B0
не заменяется последовательным умножением (1-rA)*(1-rH).

Эталон последнего ответа: HP=100, D=200, A=50/100, p=0, rA=20%, rH=30%:
общая защита 50% оставляет B1=100; C=50 уничтожает броню, O=50 снимает HP.
Итог A=0, HP=50. Повторные 30% дали бы 35 HP-урона и HP=65 — это не принято.
Прежний эталон D=200, A=60/100, rA=50%, rH=25% теперь даёт 50 A/0 HP:
сумма 75% оставляет 50 урона, который полностью поглощает броня.
Старое значение 60 A/30 HP относится к заменённой редакции, не текущей приёмке.

U/Q5: целые D/HP/броня. U, ответ 2026-09-20: после всех применимых модификаторов
подготовки урона один `floor` по объединённому типу/политике даёт D. До этой
границы дроби сохраняются; промежуточные операции и отдельные предметы не округляются.
Это округление входа не заменяет округления ветвей после разделения и защиты.
Для обычного урона: H0=floor(D*p), B0=D-H0;
B1=floor(B0*(1-R_B)); C=min(A,B1);
O=B1-C; H_direct=floor(H0*(1-R_H)); H1=H_direct+O.
Потери от сопротивлений не возвращаются
в другую ветвь. Нет принудительного минимума 1 после защиты. Дробные значения
старых профилей D1 сохраняются; переход существующих float-ресурсов в D2 требует
отдельной миграции, а не тихого округления при загрузке.

Примеры подготовки входа (U, арифметика проекта):

| Подготовка урона одного типа/политики | Значение до floor | Целый D |
|---|---|---|
| База 3, высота ×1.5, стойка ×0.7 | 3.15 | 3 |
| База 1, стойка ×0.7 | 0.7 | 0 |
| Два компонента по 0.6 после применимых модификаторов | 1.2 | 1 |

В первом примере промежуточное округление после высоты ошибочно дало бы D=2.
В последнем округление отдельных источников ошибочно дало бы D=0.
Вариант дробных ресурсов с округлением только в UI не выбран. Порядок и область
будущих модификаторов не задаются одним правилом округления. Распределение нехватки
брони между повреждающими типами принято в §4; единый итог HP смешанного попадания
принят в §2.2, допуск состояния — в §5; форма результата и семантика событий определены в §9.5.

### 2.1. Превышение 100%: восстановление HP

U, ответ 2026-09-20: при эффективном сопротивлении выше 100% соответствующая
ветвь восстанавливает HP; для броневой ветви это тоже HP, а не ремонт брони.
Пример пользователя: 10 единиц огня при эффективных 110% дают 1 HP лечения.
Речь об эффективном сопротивлении с разрешённым перками превышением, а не о
набранных 110% при неизменённом стандартном лимите 75%.

Вещественная величина восстановления для ветви X и её эффективного R>1:
G=X*(R-1). Ветвь при этом не расходует броню/HP, а восстановление не проходит
сопротивления повторно. Для R=1 ветвь полностью блокируется без восстановления.
U, ответ 2026-09-20: целое восстановление G_int=floor(X*(R-1)) при R>1;
округляется положительная величина каждой ветви, без обязательного минимума 1 HP.
Внутри попадания положительный урон и восстановление требуют раздельного учёта;
отрицательный B1 нельзя использовать как расход/распределение запаса брони.

| Ветвь, уже выделенная из попадания | Эффективная защита | Результат при достаточном недостающем HP |
|---|---|---|
| Прямая HP-ветвь: 10 огня | R_H=110%, предел разрешает | +1 HP |
| Броневая ветвь: 10 огня | R_B=110%, предел разрешает | +1 HP, без ремонта/расхода брони этой ветвью |
| Прямая HP-ветвь: 3 огня | R_H=110%, предел разрешает | floor(0.3)=0 HP |
| Прямая HP-ветвь: 19 огня | R_H=110%, предел разрешает | floor(1.9)=1 HP |
| Броневая и прямая HP-ветви по 6 огня | R_B=R_H=110%, пределы разрешают | floor(0.6)+floor(0.6)=0 HP |
| Прямая HP-ветвь: 20 огня | rH=300%, L_H=250% → R_H=250% | +30 HP |
| Прямая HP-ветвь: 20 огня | rH=120%, L_H=250% → R_H=120% | +4 HP |
| Прямая HP-ветвь: 20 огня | rH=300%, L_H=150% → R_H=150% | +10 HP |

Пределы 150%/250% — условия примеров набранных перков, не готовые перки.
Другого потолка поверх разрешённого перками нет; набранные 300% при обычном
лимите 75% по-прежнему дают R_H=75%, а не лечение.

Округление выполняется после объединения источников одного типа/политики и
разделения на ветви; дроби восстановления разных ветвей перед floor не складываются.
Floor отрицательного числа не используется: floor(-0.3)=-1 дал бы 1 HP лечения,
тогда как принятый floor положительной величины 0.3 даёт 0.
Единый итог HP, ограничение HPmax и смерть согласованы в §2.2, допуск состояния —
в §5. Результат и события смешанного попадания определены в §9.5.

### 2.2. Единый итог HP одного попадания

U, ответ 2026-09-20: весь HP-урон и восстановление одного попадания сначала
суммируются, затем здоровье меняется один раз с ограничением 0..HPmax.
Смерть проверяется по итоговому HP; временной смерти между компонентами нет.
Для живой цели с корректным 0<HP_before<=HPmax:

```text
T_damage = sum(прямой HP-урон + непоглощённый повреждающий остаток брони)
T_heal = sum(целое восстановление HP от обеих ветвей каждого типа)
HP_after = clamp(HP_before - T_damage + T_heal, 0, HPmax)
```

В T_damage/T_heal уже учтены модификаторы, защиты и округления каждой ветви.
Повреждающие суммы не ограничиваются текущим HP до сложения с лечением;
восстановление не ограничивается недостающим HP до этого сложения.
Порядок типов/источников не влияет на итог. Избыток лечения сверх HPmax не

Новый расход брони требует собственного объяснения/события: при ΔHP=0 старый
damaged не возникает. Не запускать существующее лечение «при HP-уроне» от ΔA.

DamageSource уже допускает kind status/item/cell, но это форма происхождения,
не реализованные DoT/огонь/атакующий предмет. Нынешние item reactions лечат;
новые повреждающие реакции должны создавать команды, а не вызывать Vitals напрямую.
Для будущих статусов/клеток нужен явный выбор защиты и условия наложения, без
фиктивного атакующего. Restore/from_dict, set_hp, revive и heal — не попадания.
Прямой legacy heal при over-max HP может уменьшить HP; ActionHpExecutor.heal
имеет защиту от этого. Это не обход урона, которым можно пользоваться в новом бою.

## 9. Решения ведущего, закрывающие D0 — 2026-09-21

Все пункты этого раздела имеют статус A по прямому поручению пользователя.
Они дополняют U, не меняют принятые формулы и не принимают посторонние P из
DESIGN_DIRECTION (классы, характеристики, среда, трупы, полный цикл хаба).
Названия ниже описывают будущий контракт; классы/поля/события ещё не реализованы.

### 9.1. Попадание, типы и порядок расчёта

- Один hit — одна цель и один пакет. Каждый удар серии, цель AoE, collision-жертва
  и числовое падение получает собственный hit ID. В AoE порядок целей — по unit ID;
  collision сохраняет нынешний порядок target → blocker. Не исполнять item reactions
  посреди collision-шага. Последующий hit видит уже записанное состояние предыдущего.
- После допуска команды и до расчёта hit фиксируются p, A/E/a_i, HP/HPmax, защиты,
  лимиты, свойства экипировки и применимые модификаторы. Внутри пакета их не пересчитывать.
  Реакция на исчерпание вещи — последующая команда; она не меняет прошлые компоненты.
  Проверки целостности перед/после записи сохраняются: устаревший план не применяется.
- Начальный реестр: `physical` (порядок 0), `fire` (1); будущие типы только добавляются.
  Это строковые ключи нового реестра; нынешний DamageRequest уже использует `physical`.
  Не переименовывать старые serialized enum. Равные остатки сортируются по порядку типа,
  затем по порядку политики; неизвестный тип/политика отклоняется до мутаций.
- Явные политики нового входа: `standard` (0), `hp_only_natural` (1: всё в HP через rH),
  `hp_only_unresisted` (2: всё в HP без сопротивлений). Последние две допускаются лишь
  определением эффекта с явным обходом. Они не создают armor-ветвь/расход E/a_i.
  Старый `bypass` означает иной legacy/resolved путь и не переименовывается в эти политики.
  Уже рассчитанный результат принимает только внутренний sealed исполнитель, не raw API.
- Применить базу и плоские прибавки один раз к явно указанному типу/источнику, затем
  его множители; объединить одинаковые тип/политику; применить общие входящие множители
  (стойка ×0.7 только у прямой атаки), один floor → D. Общая прибавка Силы не копируется
  в каждый предмет/тип. Отрицательную подготовленную базу ограничить нулём до множителей.
  Конверсии типов и неизвестные операции не входят в первый срез: явный отказ вместо пропуска.
- Новые определения используют точные конечные десятичные значения/рациональные множители;
  промежуточных floor нет. Сопротивления и прибавки лимита хранятся целыми сотыми процентного
  пункта (75% = 7500). Деление/остатки считаются точно; 110% от 10 обязаны дать 1 HP лечения.
  D/HP/a_i/A_i/E/V — целые единицы. Переполнение представления, NaN/inf и некорректные
  знаменатели отклоняются до мутаций; это проверка данных, не игровой потолок величин.

### 9.2. Перки и пределы сопротивлений

Для каждого типа и каждой ветви L=75%+sum(прибавок действующих перков в процентных пунктах).
Прибавки неотрицательны, независимые перки складываются; повтор одного эффекта учитывается
один раз по его instance ID. Ранги задают одну итоговую прибавку, а не все прошлые ранги.
Перк по умолчанию повышает обе ветви указанного типа; ограничение одной ветвью должно быть
явным. Предмет/заклинание может дать само сопротивление, но не повышает допустимый лимит
без явно предоставленного перка. rA/rH и лимит остаются разными величинами.

Эталоны данных: перки на +15 и +20 пунктов дают L=110%; набранные 120% дают R=110%.
Только +15 даёт L=90% при тех же 120%. Конкретные названия/ранги/редкость — баланс контента,
не незакрытый вопрос D0. Дополнительного абсолютного потолка/нижней границы сопротивлений нет.

### 9.3. Владение запасами, ключи и RNG

- Обычный максимум первого среза даёт только экипировка: Amax=sum(A_i).
  Отдельный врождённый расходуемый запас не добавляется; врождённая защита задаёт rH.
  A_i задаётся определением вещи и не меняется посреди боя. Если отдельное улучшение
  вне боя меняет A_i, a_new=min(a_old,A_new): роста текущей брони бесплатно нет,
  отсечённый остаток при снижении max не превращается в E. Само улучшение/крафт не входит в D2.
- a_i хранится на экземпляре. Нынешний item_instance_id уникален внутри owner,
  поэтому ключ порядка/armor identity — сохранённая пара (owner ID при создании,
  item_instance_id при создании). Она не меняется при переодевании/переносе;
  текущий owner/placement хранится отдельно. Дубликат ключа в состоянии отклоняется.
  Новый экземпляр получает полный запас только при явном создании, restore не ремонтирует.
- До случайного выбора вычисляется только предметный остаток:
  C_items=max(0,C_total-E_before); это C из §4.1. Взвешенный выбор сортирует кандидатов
  по стабильному ключу; при оставшемся C_items>0 и двух или более кандидатах вызывает
  injected `ActionRngPort.next_int(&"combat", sum(A_i))` один раз.
  Выбирается интервал накопленных весов, содержащий r: 0<=r<sum(A_i).
  При C_items=0 или одном кандидате draw отсутствует. После исчерпания предмета — новый выбор;
  правило действует и если урона достаточно, чтобы исчерпать всех. Ошибка RNG не заменяется
  первым предметом. Нужен пригодный к clone/restore порт, не глобальный rand/randi.
- Admission/forecast/чистый план работают с клоном RNG только для C_items. В исполнении
  сначала списывается E, затем, если план действительно сделал draws, конечное RNG-состояние
  фиксируется непосредственно перед первым списанием a_i. При C_items=0 или отсутствии
  draws нет и RNG commit. E_before=15, C_total=10 → E_after=5, вещи и RNG неизменны.
  Fault до RNG commit сохраняет уже записанный E-prefix без расхода RNG; fault после commit
  сохраняет потраченные draws и фактический prefix. Отказ до применения не расходует RNG.
  После каждой записи/сигнала нужен checkpoint; точные binding/seal DTO задаёт пакет D2.
- E — сумма записей на персонаже: grant ID, source ID, остаток, срок. По умолчанию срок —
  окончание породившего боя; явный перк может дать `persistent` до расхода/явного снятия.
  Условие срока фиксируется при получении; новый перк не продлевает старые записи задним числом.
  Новый каст добавляет запись, не освежает старую. Расход — сначала ближайший срок,
  затем grant ID; persistent после обычных. Всё это раньше расхода a_i, без нового RNG.
  Переодевание не переносит E на вещи. Конец боя удаляет только истёкшие записи один раз.
- Снимок переносит a_i/armor identity, записи E/счётчик grant, ключи источников, экипировку,
  сопротивления/перки и RNG без live-ссылок. Старый ARMOR не переосмысляется; legacy snapshot
  остаётся legacy, подключение нового блока требует явного адаптера данных. Для нового блока
  отсутствующие обязательные данные/неизвестная версия — отказ, не автозаполнение полной бронёй.

### 9.4. Восстановление и ремонт

- Объём заклинания V=max(0,floor(подготовленный объём)): плоские прибавки, затем множители,
  без промежуточного округления. Нет минимальной единицы. Успешный каст оплачивается полностью
  по определению способности независимо от доли обычной/временной брони; частичного возврата нет.
  В бою V>0 может целиком стать E даже при Amax=0. При V=0 — отказ без оплаты/мутации.
- Вне боя восстановление W=min(V,M), E не создаётся. При M=0 — отказ без оплаты;
  при 0<M<V восстанавливается M за полную цену каста, неиспользованный объём не сохраняется.
  Уже разрешённые перком persistent-записи не удаляются и не восстанавливаются этим действием.
  Объём/цена конкретных заклинаний задаются данными отдельного контентного среза;
  эталон расчёта D2 — V=20, без введения новой системы маны ради брони.
- Рабочий ресурс ремонта — «ремонтные материалы», общий целый запас отряда.
  Начальный курс: 1 материал за 1 фактически восстановленную единицу обычной брони.
  Будущая настройка курса не меняет принцип оплаты по факту; отдельную прочность не вводить.
- Между уровнями игрок выбирает одну вещь или набор надетых вещей персонажа и целый
  бюджет материалов. B=min(запрошенный бюджет, запас отряда); W=min(B,сумма недостач выбранных).
  W распределяется пропорционально недостаче с тем же floor/крупнейшими остатками/ключом,
  что заклинание, но только по выбранным вещам. Оплата ровно W; при W=0 ничего не тратится.
  Ремонт не создаёт E. Например, недостача 30/10 и бюджет 3 → восстановление 2/1, цена 3;
  недостача 5 и бюджет 20 → восстановление 5, цена 5. UI/добыча ресурса/хаб — отдельный D4.

### 9.5. Результат, события, состояния и последствия

- Результат hit содержит hit ID/source, p, по типу/политике D/H0/B0, эффективные защиты,
  H_direct/armor overflow/HP-damage/healing, итоговые T_damage/T_heal, HP_before/after,
  расход E/a_i и RNG до/после. `hp_loss=max(0,HP_before-HP_after)`,
  `hp_gain=max(0,HP_after-HP_before)` отделены от gross HP-damage и лечения.
- Guarded порядок применения: E → RNG commit только при наличии draws для C_items>0
  (§9.3) → изменённые a_i в порядке стабильного ключа →
  одна запись HP → текущая цепь смерти/occupancy. После каждой записи/сигнала проверять
  владельцев/состояние; fault сохраняет исполненный prefix и не публикует фиктивный полный hit.
  Это не транзакционный rollback. Записи с нулевой дельтой пропускаются.
- Объяснение и событие изменения брони отражают реальный расход/восстановление отдельно
  от HP. Завершённый `hit_resolved` отражает полный результат, включая нулевой итог HP.
  Существующий смысл `damaged`/`healed` сохраняется: только фактическая потеря/прирост HP,
  никогда одновременно от одного net-итога; `died` — один переход живой → мёртвый.
  Действующее лечение предметом «при HP-уроне» получает hp_loss; armor-only/net-zero
  попадание его не запускает. HP_changed тоже отражает только итоговую запись.
- Допуск состояния берётся из положительной нужной повреждающей HP-части конкретного
  hit до лечения, а не hp_loss. Он сохраняется в результате. Отдельная команда состояния
  исполняется после mandatory spatial-последствий исходного hit, перед optional item reactions;
  повторно проверяет живую цель, источник и иммунитет. Чужой hit/collision не подменяет допуск.
  Сам тип урона не накладывает состояние: источник должен его содержать явно.
  Первый D3-кандидат — кровотечение от физической части; длительность/stack/tick —
  контентный пакет D3. Нет состояния на мёртвой цели и автоматического снятия старого состояния.
- По умолчанию состояние атаки требует HP-часть своего типа. Явная политика перка
  может обойти только это требование; иммунитет сохраняется. Контактное состояние среды
  задаёт отдельную политику без HP-gate; DoT задаёт собственные hit/тип/защиту и не копирует
  первичное наложение рекурсивно. Конкретные smoke/DoT не входят в D2.
- Сохраняются цена/срок стойки, impact ×0.5, отдельный канал равновесия и его пороги.
  Collision и падение — физические `standard` hit, без дополнительного ×0.7 от стойки.
  Базы collision, порядок target/blocker и forced/voluntary пороги/база падения остаются
  нынешними; старый вычет ARMOR и minimum-1 из защиты заменяются новым resolver/floor.
  Пропасть и нынешние летальные клетки остаются прямой смертью, без hit/состояния по U2.

### 9.6. Что остаётся следующим этапам

D0 не требует дальнейшего опроса. D1 извлекает нынешнюю формулу без изменения поведения;
D2 получает точный пакет API/schema/checkpoints и реализует согласованный вертикальный срез;
D3 выбирает конкретное состояние/баланс, D4 — контент/экономику ремонта и переходы,
D5 — среду. Сигнатуры, номера schema и реализация адаптеров выбираются ведущим по коду,
а не считаются существующими API из текста D0. Ни один этап не начат этим документом.
Перед кодом необходимы отдельное поручение и пакет по CODEX_WORKFLOW. При конфликте с
принятыми U — обращение к пользователю; обычные детали решаются ведущим самостоятельно.
