# R — Фундаментальные правила (введены аудитом)

## R-1. `Resource` = ассет/определение. `RefCounted` = рантайм-состояние. ЖЁСТКО

**Причина введения:** дефект C-3. `ResourceLoader` **кэширует** `.tres` — один
экземпляр разделяется между ВСЕМИ владельцами. Хранение per-owner состояния
внутри `Resource` привело к hard error Godot
(`Signal is already connected to given callable`) и к перезатиранию владельца
при выдаче одного предмета двум юнитам. Модуль 5 был неработоспособен при
более чем одном экземпляре предмета в игре.

| Базовый класс | Назначение | Создаёт | Мутабельность | Примеры |
|---|---|---|---|---|
| `Resource` | «**Что такое** X» — определение, ассет `.tres` | дизайнер в редакторе | **immutable в рантайме** | `ItemDef`, `AbilityDef`, `StatDef`, `TileDef`, `EnemyDef`, `AIBehaviorProfile`, `AIConsideration`, `TurnOrderStrategy`, `DamageModifier`, `IsoGridConfig`, `LootTable` |
| `RefCounted` | «**Конкретный** X прямо сейчас» — состояние | код | мутабельное | `UnitState`, `Vitals`, `StatsBag`, `ItemInstance`, `ItemEffectRuntime`, `BattleBoard`, `DamageContext`, `DamageInfo`, `AIAction`, `AIDecisionContext`, `Command` |
| `Node` | представление (View) + то, чему нужен `_process`/дерево сцены | сцена/код | — | визуалы, контроллеры, адаптеры |

**Правила-следствия:**
- Если у класса есть поле вида `_bound_owner` / `_bound_unit` / `current_*` /
  любое состояние конкретного экземпляра — он **обязан** быть `RefCounted`.
- Никогда не мутировать `Resource` в рантайме (в т.ч. не писать в него `item_id`).
- Транзиентные DTO (живут кадр/расчёт) — всегда `RefCounted`, никогда `Resource`
  (`Resource` тянет RID и инфраструктуру загрузки, а без `@export` всё равно
  не сериализуется — то есть даёт только накладные расходы).
- Паттерн для контента: **Def/Instance split** —
  `XDef : Resource` (данные) → `XInstance : RefCounted` (состояние + ссылка на def).
- Чистая логика без состояния — `static` функции на `RefCounted`-классе (как
  `IsoGridUtils`, `PushResolver`). Это корректно и сохраняется.

**Мнемоника:** `Resource` отвечает на «что такое Меч», `RefCounted` — на
«этот конкретный меч у этого юнита с 3 зарядами».

> Оговорка к популярному совету «используйте Resource на 100%»: он верен для
> **контента** (дизайнер создаёт `.tres` руками, код принимает их и применяет),
> но буквальное прочтение «на 100%» и породило C-3. Формулировка выше —
> уточнённая версия этого совета.

## R-2. Attribute ≠ Vital. Никогда не писать текущее значение в `Stat.base_value`

**Причина введения:** дефект C-2 — порча данных. `get_value()` = `base_value`
+ модификаторы; запись результата обратно в `base_value` **впекает модификаторы
в базу**. Воспроизведение: HP base=10, амулет `+5` → `get_value()=15`; урон 3 →
`set_base_value(12)` → `get_value()=17`. **HP вырос от полученного урона**, а
снятие амулета оставляло `+2` навсегда.

| Понятие | Природа | Примеры | Где живёт |
|---|---|---|---|
| **Attribute** (характеристика) | **производное** значение: `base + модификаторы`, вычисляется чисто | `HP_MAX`, `BALANCE_MAX`, `STRENGTH`, `IMPACT_POWER`, `MOVE_RANGE`, `INITIATIVE` | `Stat` / `StatsBag` |
| **Vital / Pool** (ресурс) | **состояние**: текущее значение, мутируется, клампится по производному максимуму | `hp_current`, `balance_current`, `move_points_left` | `Vitals` |

- `HP` и `BALANCE` **удалены** из `StatTypes` — баг становится физически невозможным.
- Все мутации HP/Balance — только через методы `Vitals`
  (`apply_damage` / `heal` / `add_impact`), которые **клампят** и **эмитят сигналы**.
- Смерть — ответственность `Vitals` (`hp <= 0` → сигнал `died`), а не вызывающего кода.
- `StatsBag` не отдаёт наружу мутабельный `Stat` — иначе невозможно гарантировать
  инварианты и сигнал об изменении (в старом `StatsComponent.get_stat()` это
  приводило к тому, что урон/лечение обходили `stat_changed`, и UI не видел HP).

## R-3. `scripts/core/**` НЕ имеет права ссылаться на автозагрузки по имени

**Причина введения:** дефект S-4. `DamageCalculator` (static!) эмитил напрямую
в `GameEventBus`, `InventoryComponent` тоже. Следствия: логику нельзя
протестировать без поднятия автозагрузок; нельзя иметь изолированную симуляцию
(нужна для AI-lookahead, реплеев и sandbox-превью).

- Внешние зависимости (шина событий, RNG, доска, очередь действий) **инжектируются**.
- Шина событий — через абстракцию `EventSink`: в игре адаптер над `GameEventBus`,
  в тестах `RecordingEventSink`, в AI-lookahead `NullEventSink`.
- Автозагрузки допустимы только в `scripts/gameplay/**` (View) и `scripts/test/**`.

**Направление зависимостей (обратные — запрещены):**
```
math/grid  →  board  →  units/stats  →  combat  →  actions  →  ai  →  flow  →  view
```

## R-4. Идентичность и сериализация закладываются сразу, а не в модуле 12

**Причина введения:** C-1 + G-2. Требование «Profile System + несколько слотов
сохранений» невыполнимо, если у юнита нет стабильного id, статы — enum-индексы,
а состояние живёт в нодах.

- Юнит идентифицируется **`UnitId`**, а не ссылкой на компонент статов.
  **`StatsComponent`/`StatsBag` — НЕ идентичность юнита.**
- Любой класс рантайм-состояния получает `to_dict()` / `static from_dict()`.
- `StatTypes` enum: **только добавлять в конец, никогда не переупорядочивать и
  не удалять из середины** — иначе числовые индексы сдвинутся и сломают старые
  save-файлы и `.tres`. (Долгосрочно — заменить на `StringName` + реестр `StatDef`.)
- Сохранения версионируются (`save_version`) с самого первого формата.

## R-5. Никакого недетерминированного RNG в игровой логике

**Причина введения:** G-1. Глобальный `randf()` делал порядок ходов
невосстановимым после загрузки; для роглайка воспроизводимость сида
обязательна (реплеи, шаринг сидов, отладка баг-репортов).

- Только `RngService` с именованными потоками (`&"combat"`, `&"loot"`, `&"gen"`),
  состояние каждого потока сохраняется/загружается.
- Тай-брейки в сортировках и выборе действий AI — **явные и детерминированные**
  (например по `(score, cell.y, cell.x, unit_id)`), а не «первый встреченный».

## R-6. Превью = сухой прогон настоящей команды, а не отдельная функция расчёта

**Причина введения:** D-6.5. Требование «обязательный предпросмотр результата»
означает parity превью и результата. Отдельная функция расчёта даёт parity
«по договорённости» (её легко нарушить, добавив эффект только в apply-путь);
прогон той же команды на копии состояния даёт parity **по построению**.

- `Command.preview(board_copy)` и `Command.execute(board)` — один код.
- Превью обязано учитывать полную цепочку: push → коллизии → урон → смерти →
  эффекты тайлов → срабатывание предметов.

## R-7. Порядок работ: вертикальный срез до контента

**Причина введения:** P-1 + G-5. Модули 5/6/7 помечены `Done`, но содержали
дефекты, которые обнаружились бы на первой минуте реального игрового цикла
(C-2 проявляется при первом же уроне юниту с предметом). Они не были найдены
за 7 модулей, потому что игрового цикла нет — есть 5 изолированных дебаг-панелей
с захардкоженными числами. Системы построены, но **никогда не встречались**.

- Пока не работает полный цикл (ход → атака → толчок → смерть → победа →
  выбор награды → новая карта) на квадратах-заглушках — **новый контент не
  добавляется** (второй тип врага, второй предмет, процедурная генерация).
- Статусы модулей: `Draft` → `Implemented` (код + headless) →
  `Verified` (+ unit-тесты и/или подтверждённая визуальная проверка).
  **`Implemented` ≠ `Done`.**
- Критерий коммита: зелёный headless-прогон **и** (визуальная проверка **или**
  зелёные тесты).

## Координаты и ввод
- Все сигналы `InputManager` несут **viewport (screen) координаты**.
  Любой потребитель, которому нужны мировые/grid координаты, ОБЯЗАН сначала
  перевести их через `get_viewport().get_canvas_transform().affine_inverse()`.
  Иначе клики "уплывают" при панорамировании/зуме камеры.
  См. `debug_grid_visualizer._to_world()` как пример.
- `InputManager` (Модуль 1) ничего не знает о сетке/боевой логике — только
  нормализует mouse/touch/gestures в сигналы. Grid-математика — в `IsoGridUtils`
  (чистые статические функции, без состояния).
- Высота тайла резолвится итеративно через `IsoGridUtils.resolve_grid_with_height()`
  с `height_query: Callable`, а не напрямую — клик рядом с уступом иначе может
  попасть на неверную клетку.

## Рендеринг / сортировка (Модуль 2)
- Слои фиксированы через `RenderLayers.Layer` enum + `z_index`:
  `GROUND_EFFECTS(0) < TILES(100) < ENTITIES(200) < PROJECTILES(300) < VFX_OVERLAY(400) < UI_PREVIEW(500)`.
- Внутри `ENTITIES` — встроенный Godot Y-sort (`y_sort_enabled=true` на родителе).
- `YSortable`: позиция для сортировки берётся при **height=0** (`grid_to_screen(anchor, config, 0)`),
  визуальный подъём — ТОЛЬКО через `get_visual_offset()`, не через `position`.
  Иначе высокая клетка "перепрыгивала" бы порядок сортировки.
- **ПРАВИЛО**: плоский пол — всегда в `TILES`, никогда не участвует в overlap
  с юнитами. Любой объект с визуальной высотой/объёмом (платформы, укрытия,
  стены), который должен визуально ПЕРЕКРЫВАТЬ юнитов — должен быть в
  `ENTITIES` через `YSortable`, а не частью плоской тайловой сетки.
  **РЕАЛИЗОВАНО** как `ElevatedTileVisual : YSortable`
  (`scripts/core/rendering/elevated_tile_visual.gd`) — рисует объёмный блок
  (верхняя грань + боковая грань-риsер), сортируется по `grid_anchor` на
  height=0 как обычный `YSortable`, с эпсилон-сдвигом `-1.0` по Y, чтобы при
  равном сортировочном ключе платформа рисовалась чуть раньше (позади) юнита,
  стоящего на ней. Плоская тайловая сетка (`debug_grid_visualizer.gd`) теперь
  ВСЕГДА рисует пол на height=0 и не рисует возвышения сама — вместо этого
  динамически спавнит `ElevatedTileVisual` в `EntitiesLayer` для каждой
  клетки из `elevated_cells` (единственный источник правды, используется и
  для рендера, и для `height_query()` пасфайндера — без дублирования данных
  и без хардкода конкретных клеток в коде отрисовки).

## Pathfinding (Модуль 3)
- Движение только по 4 направлениям (без диагоналей) — как в Into the Breach.
- Правило высоты: переход между соседними клетками запрещён, если
  `|height(a) - height(b)| > max_height_step` (по умолчанию 1).
- **ОТКЛОНЕНИЕ ОТ ПЛАНА**: изначально планировался `AStarGrid2D`, но он не
  умеет запрещать конкретные РЁБРА графа (только точки целиком через
  `set_point_solid`/`set_point_weight_scale`). Правило высоты — edge-правило
  (зависит от пары клеток), поэтому `AStarGrid2D` дал бы разные правила
  проходимости для `find_path` и `get_reachable_cells`. Решение: `AStarGrid2D`
  убран полностью, `GridPathfinder` использует собственный Dijkstra для ОБОИХ
  методов с общей `_can_move_between()` — гарантия согласованности.
- Данные о карте передаются через `GridDataProvider` (набор `Callable`:
  `is_walkable`, `get_height`, `get_move_cost`) — Dependency Inversion,
  pathfinder не знает, как устроена реальная карта/юниты/эффекты.
- Зона хода (`get_reachable_cells`) — это НЕ A*, а flood-fill с ограничением
  по суммарной стоимости (`max_cost`), т.к. A* ищет путь к одной цели, а не
  множество достижимых клеток.

## Stats & Initiative (Модуль 4)
- `STRENGTH` (прямой урон) и `IMPACT_POWER` (толкание/накопление Баланса) —
  ЭТО РАЗНЫЕ характеристики. Не путать и не объединять — это разные оси
  геймдизайна (можно бить сильно, но не толкать, и наоборот). **Актуально.**
- Stat = `base_value` + список `StatModifier` (Resource с `source_id`,
  `operation` ADD_FLAT/ADD_PERCENT/MULTIPLY, `priority`). Значение кэшируется,
  пересчитывается только при изменении модификаторов — важно для мобилок.
  - ⚠️ **ЧАСТИЧНО ОТМЕНЕНО (R-2, D-4.1).** `HP`/`BALANCE` больше не статы —
    это Vitals. `priority` удаляется в пользу фиксированного конвейера стадий
    `(base + Σflat) * (1 + Σpercent) * ∏mult`: смешивать ADD_PERCENT (считается
    от базы) и MULTIPLY (от накопленного) в списке, отсортированном по
    `priority`, семантически неопределённо, и результат зависел от порядка
    добавления модификаторов. Кэширование — сохраняется.
- `StatModifier.source_id` — обязателен для снятия ВСЕХ модификаторов
  конкретного источника (предмет/перк/статус) при его потере/окончании, без
  необходимости отдельно откатывать эффекты вручную.
- Порядок ходов — Strategy pattern через `TurnOrderStrategy : Resource`
  (абстрактный, метод `compute_order`). Подмена формулы — просто замена
  `.tres` ресурса, без изменения кода. `SimpleInitiativeStrategy` — выше
  `INITIATIVE` ходит раньше, случайный tiebreak при равенстве (по требованию
  пользователя — рандом, а не стабильный порядок по ID).
- `InitiativeTimeline` НЕ управляет фазами боя (это Battle Flow State Machine) —
  только порядок и очередь ходов. **Актуально.**
  - ⚠️ **ДОПОЛНЕНО (D-4.6, D-4.7).** Курсор должен храниться по стабильному
    `UnitId`, а не по индексу в массиве: `unregister_participant()` вызывает
    `recompute_order()`, который сбрасывал `_current_index = -1` — то есть
    смерть юнита посреди раунда **перезапускала раунд**, и все уже ходившие
    получали ход снова. Также нужны сигналы `round_started`/`round_ended` —
    без них tick-based Status Engine нереализуем.

## Экономика действий: Движение и Атака (правило геймдизайна, влияет на Модули 6/8/10)
- **Move** и **Attack** — РАЗНЫЕ действия, использующие общий пул очков хода
  (`MOVE_RANGE`). Ближний бой: дальность атаки = 1 смежный тайл.
- **Поток A (раздельно)**: подвигаться (потратить часть очков хода) → атаковать
  (если враг в радиусе) → остаток очков хода всё ещё доступен ПОСЛЕ атаки
  (move → attack → move в одном ходу).
- **Поток B (комбо через UI)**: юнит выбран, игрок таргетит врага, находящегося
  в пределах (остаток дальности хода + радиус атаки) → по подтверждению юнит
  АВТОМАТИЧЕСКИ доходит до клетки рядом с врагом и сразу атакует. Механически
  это всё равно Move, затем Attack — просто объединено в одно подтверждение
  для UX.
- **СЛЕДСТВИЕ ДЛЯ API**: `DamageCalculator`/`ActionPreview` и подобные системы
  ДОЛЖНЫ принимать явный `attacker_cell` (гипотетическая позиция ПОСЛЕ
  движения), а не читать "текущую" позицию юнита с сетки. Иначе комбо-поток B
  не сможет показать превью урona/толкания ДО фактического перемещения.
  Уже заложено в контракте Модуля 6 (`calculate()` принимает `attacker_cell`/
  `target_cell` параметрами, не читает их из живого состояния юнита).

## Общие правила GDScript (весь проект)
- Strictly typed GDScript 4.x всегда.
- `var x := some_dictionary[key]` НЕ РАБОТАЕТ для вывода типа при индексации
  Dictionary в строгой типизации ("Cannot infer the type..."). Всегда делать
  через промежуточную типизированную переменную:
  `var tmp: SomeType = dict[key]` затем использовать `tmp`.
- SOLID: Data/Logic (`scripts/core/**`) отделены от View/Nodes
  (`scripts/gameplay/**`, `scripts/test/**`). `Resource` — для предметов,
  перков, формул, способностей (не хардкод в скриптах).
