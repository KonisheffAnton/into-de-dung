# Архитектурные инварианты

Актуальная редакция 2026-09-20. Здесь основания технических ограничений;
состояние реализации — [ARCHITECTURE](ARCHITECTURE.md), процесс — [AGENTS](../AGENTS.md).
Идентификаторы R-1..R-7 сохранены для старых ссылок. История — [архив](DECISIONS.history-20260920.md).

## R-1. Resource = определение, RefCounted = runtime

Разделяемые определения не содержат владельца, текущие заряды или иное состояние
экземпляра. Для каждого владельца создаётся независимый runtime; Node отвечает
за представление/жизнь в сцене. Значимые определения фиксируются/копируются согласно
контракту механизма, чтобы изменение исходного Resource не меняло идущую симуляцию.
Причина: кэшируемый Resource раньше разделял изменяемое состояние между владельцами.

## R-2. Производный параметр и текущий запас разделены

StatsBag вычисляет bases и modifiers; текущие HP/balance принадлежат Vitals,
остатки действий — ActionResources. Не записывать результат с модификаторами обратно
в base_value: это повторно прибавляет бонус и портит состояние после снятия предмета.
Обычные изменения HP/balance идут через методы владельца; restore использует
предусмотренный тихий путь, не имитирует лечение или смерть.
Balance сейчас означает накопленный impact до порога, а не вторую полосу здоровья.
Сила прямого удара и IMPACT_POWER — разные параметры.

## R-3. Зависимости ядра инжектируются

Код `scripts/core/**` не обращается к автозагрузкам по имени. Доска, правила,
события и RNG поступают через зависимости. Игровое исполнение и симуляция
должны работать с разными экземплярами состояния без глобального общего владельца.
Позиции меняются через BattleBoard; GridDataProvider получают от доски.
Внешний event sink публикует значения результата и не мутирует бой.
Реакции формируют команды для очереди, а не исполняют скрытые изменения из callback.

## R-4. Идентичность, владение и сериализация

Юнит идентифицируется UnitId; StatsBag/Node не подменяют идентичность. Предметы и
occurrences имеют собственное владение/ID по контракту соответствующей подсистемы.
Сериализуемые enum только дополняются. Снимки версионируются, raw-типы, ссылки,
capability и ограничения проверяются до allocation/мутации согласно контракту.
Новые влияющие данные добавляются вместе с validation/copy/restore и миграцией.
Неизвестные/неподдерживаемые данные отклоняются явно, не пропадают из прогноза.
Restore не делает equip/refill, не меняет глобальные счётчики и не копирует live listeners.
Нынешние simulation snapshots и legacy save DTO имеют разные гарантии; ни один
не объявляется сохранением всего забега. Точные совместимые bytes — в frozen пакетах.

## R-5. Детерминизм

Игровая случайность проходит внедрённый RNG с переносимым состоянием.
Порядок команд, реакций и модификаторов, ID и tie-breaks задаются явно;
обход коллекции или порядок UI-вызовов не должны незаметно менять результат.
Не обещать поддержку произвольного RNG: forecast проверяет способность клонирования.

## R-6. Прогноз исполняет настоящие команды

Прогноз создаёт изолированное состояние со всеми влияющими предметами, ресурсами,
правилами и RNG и исполняет ту же команду с полной цепью последствий/реакций.
UI читает результат, не содержит отдельной формулы боя. Проверять как совпадение
результатов, так и неизменность live-состояния. Текущий реализованный интерфейс —
[AttackForecast](ATTACK_FORECAST.md); общего PreviewToken API пока нет.

## R-7. Ограниченный рабочий срез

Завершать наблюдаемый игровой результат с приёмкой до расширения контента и
обобщений. Исторический буквальный запрет второго предмета заменён позднейшими
поручениями: флакон и печать уже существуют. Это не разрешение выполнять весь backlog.
Проект/реализация/проверка — разные статусы; факт тестов имеет дату и commit.
Новая механика может требовать обработчика и тестов; требование расширяемости
не означает универсальный DSL или поддержку любого скрипта из snapshot.

## Ввод, пространство и представление

InputManager передаёт viewport-координаты; потребитель преобразует их через свой
canvas transform перед grid-расчётом, учитывая высоту. Pathfinding получает
геометрию через provider; reachability и путь используют согласованные edge-правила.
Исполнение движения и его оплата подчинены MoveRules/SpatialRules, а не старой
формуле поиска пути. Нынешние тайлы, стены и фигуры сохраняют общий ENTITIES
Y-sort; не возвращать правило из старого полигона «весь пол только в TILES»
к текущему демо. Принятые пространственные guards/receipts — §4.5
[P08 r3](P08_SPATIAL_TASK_R3.md), без пересказа/изменения frozen текста здесь.

Strictly typed GDScript; комментарии по-русски объясняют причину.
Из Dictionary извлекают значение с нужной явной типизацией там, где вывод типа
не определён. Старые debug-сцены сохраняют свои контракты/проверки;
ярлык «тестовый код» сам по себе не разрешает его произвольное удаление.
