# Владение исполнением и представлением общего боя

Реализованная граница 2026-09-26. В обычном `BattleDemo` для точного класса
`BattleCoreReactionsSession` движение, все нынешние действия, граница хода и
один шаг ИИ исполняются через `BattleExecutionWorker`. Расстановка и выбор
остаются на основном потоке. D4, инициатива, прежние fixtures и прямой session API
сохраняют синхронный путь. Это ограничение области, а не смена правил боя.

## Передача владения

До запуска main очищает прогнозы и передаёт существующую session одному worker.
`session`, `_battle`, `board_view.session` у UI очищены; идентичность страницы
действий хранится числовым instance ID, без ссылки на session;
`is_execution_pending()` запрещает повторное действие, выбор, осмотр, подготовку
прогноза и refresh. На основном потоке остаются только значения завершённого
представления. Ссылки на runtime, ранее полученные внешним кодом, нельзя читать
или менять между start и join; API не является общим конкурентным сервисом.

Worker принимает только перечисленные session-методы и скалярные аргументы
(ID, режим, Vector2i). Перед каждой передачей обходится граф session/state/context:
точные штатные классы, штатный RNG и пустой ActionEventSink, отсутствие внешних
подписок на runtime и Resource. Единственная разрешённая подписка — проверенный
синхронный callback смерти именно этой доски/юнита/vitals. Неизвестный класс,
Callable/Signal в данных, внешний listener, превышение лимита обхода или ошибка
старта потока возвращают исполнение на основной поток. Подписки не отключаются.
Завершённый receipt не исполняется повторно и не входит в обход; очередь входит
в аудит, должна иметь точный штатный класс и быть свободна.
Проверка владения не сертифицирует допустимость мира и не кэшируется по revision.

В потоке исполняется настоящий session-метод с pathfinding/BT, строгим admission,
ActionQueue, синхронными внутренними callbacks и всей очередью реакций. Отдельного
preview/commit или отката нет. RNG, ID помощников и counters принадлежат runtime;
этот путь не вызывает глобальный UnitId allocator. Session проверяет исход после
полного submit; INTERRUPTED/FAULTED сохраняют прежний выполненный prefix.

Main опрашивает окончание без ожидания и получает session/result через
`wait_to_finish` только после завершения. Затем возвращает владение UI, публикует
receipt/журнал/исход и делает полный refresh. Пока результат не принят, следующий
шаг ИИ не запускается. Reset, смена сценария и выход сначала join; прежний result
отбрасывается, только затем runtime закрывается/пересоздаётся. Это ожидание может
задержать сам reset/выход, но не обычные кадры ожидания команды.

## Согласованный вид

`BattleUnitView` содержит значения ID, фракции, имени, HP, равновесия и пределов.
`BattleDemoIsoVisual` не хранит UnitState/StatsBag/Vitals. `BattleDemoBoard.refresh`
захватывает высоты, terrain, клетки бойцов, визуальные флаги, броню и среду.
Redraw, resize, overlays и геометрия используют эту проекцию; при pending
hit testing заблокирован, предыдущий мир остаётся видимым. Текст и descriptors
также сохраняют последний завершённый вид; статус сообщает об исполнении.
Свежий refresh обновляет и прямые изменения без revision. Это presentation DTO,
не save-game и не допуск команды. Старые отложенные redraw не держат live unit.

Подготовленные прогнозы по-прежнему изолированы и могут завершиться параллельно;
их устаревшие результаты не публикуются. Клик не ждёт прогноз и заново проверяет
состояние при исполнении. Механизмы прогнозов принадлежат ATTACK_FORECAST.

## Проверки и границы приёмки

`test_battle_execution_worker.gd`: sync/worker receipts, snapshots, RNG/counters,
ресурсы/ID, все действия, обе границы и шаги ИИ, отказ и FAULTED, запрет внешних
callbacks/custom RNG/sink. `test_battle_execution_ui.gd`: настоящий клик,
изоляция вида, все входы во время pending, resize/redraw, публикация helper,
синхронный callback fallback, reset/смена сцены/выход, FAULTED и PNG.
Связанные прежние UI runner ожидают именно завершение live job до чтения runtime.

Подготовка прогнозов, аудит владения, refresh и перестройка узлов остаются на
main и имеют измеримую стоимость. Полная плавность не обещана: нужны A/B на той
же машине и один общий пользовательский плейтест; результаты — HISTORY/отчёт.
