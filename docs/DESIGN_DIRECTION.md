## 1. Оценка

Сильная сторона проекта — работающий бой с общей очередью последствий и реальным
изолированным прогнозом. Сохранять это основание. Полное переписывание ядра
не обосновано. Однако хорошие проверки нынешних правил не доказывают готовность
к произвольным типам урона, броне как ресурсу, состояниям или хабу.

Главные разрывы: фиксированные формулы/специальные поля контента; отсутствие
игрового цикла между боями; смешение текущих фактов с историей в документации.
Приоритет — проверять новый дизайн малыми игровыми срезами, сохраняя прогноз,
а не строить универсальный движок для всех воображаемых механик.

P: основа идентичности игры — маг собирает команду и сочетания предметов,
а на поле выигрывает порядком действий, позицией и взаимодействиями среды.
Броня добавляет выбор «разрушить защиту → открыть доступ состояниям».
Риск: толстая броня превращает бой в обязательное ожидание до начала интересных
эффектов. Проверять время до первого воздействия на HP, ценность чистого урона
против состояний и способы обойти защиту; не добавлять обход всем по умолчанию.

U: экипировка возвращается при неудаче. P: это поддерживает эксперименты со сборками.
Q: цена провала — потеря добычи забега, времени, наёмников или иной ресурс?
Не вводить уничтожение экипировки вопреки запросу. Судьба персонажей и добычи,
условия успеха и постоянная прогрессия ещё не описаны.

## 3. Параметры и характеристики — рекомендации P

Разделить три понятия: постоянное определение/производное значение; текущий запас;
наличие способности пользоваться системой. Числовой ноль не заменяет отсутствие
способности. Отсутствие брони не то же самое, что надетая броня с исчерпанным запасом.
Дополнительный параметр может иметь нейтральный ноль в расчёте без строки в UI.
У врождённого свойства тоже есть источник: «дополнительное» не означает только вещь.

| Параметр | Рекомендуемая категория | Отображение |
|---|---|---|
| HP max/current, balance max/current | Основа всех боевых юнитов; нынешний balance накапливает impact к порогу, затем сбрасывается | HP и состояние равновесия; не смешивать запас с накопленным нарушением |
| Перемещение, main, bonus | Общие ресурсы боя; максимумы и остатки отдельно, разрешённый максимум может быть 0 | Остаток/максимум; цена конкретного действия |
| Сила атаки/оружия | Входные значения; «итоговый урон» — результат выбранной атаки | База по типам в карточке, точный итог против цели в forecast |
| Дальность | Свойство выбранной атаки/оружия, не единая дальность всех способностей | Дальность базовой атаки плюс сведения каждой способности |
| Броня max/current и её сопротивления | Дополнительная способность от экипировки или явно заданной врождённой защиты | Полоса при наличии; разбитую броню не скрывать как отсутствующую |
| Естественные сопротивления | Общий запрос по типу с нейтральным 0; ненулевые значения приходят из источников | Отдельно от сопротивлений брони, подробно по типам |
| Мана max/current, сила заклинаний | Дополнительная способность для использующих магию; может быть врождённой | Показывать при наличии, не только при ненулевой текущей мане |
| Регенерации, вампиризм | Дополнительные свойства с нулевым нейтральным значением | В расширенных сведениях; нужны триггер, база и ограничения |

Не все перечисленные параметры уже есть в коде. Не добавлять их enum/поля
пакетом ради будущего UI. Рекомендуется добавить в сведения **силу воздействия
на равновесие**: она важна для существующих толчков, но отсутствует в списке U9.
В бою сначала показывать HP/броню/равновесие/ресурсы действий и доступные способности;
сопротивления, источники бонусов и прочие подробности — раскрываемым блоком.

Четырёх характеристик для первого варианта достаточно. P: не расширять список,
пока не проверено, даёт ли каждая самостоятельный выбор. Рост Силы должен влиять
на явно помеченные атаки; не добавлять её к огню клетки или каждому магическому
компоненту. Выносливость усиливает выживание/устойчивость, Интеллект — магию.

Критический риск Ловкости: ещё 1 main при базе 1 может удвоить число атак,
одновременно с ростом движения и bonus. P: сначала малые линейные изменения
движения/эффективности, а дополнительные действия — редкий явно оценённый эффект.
Если сохранить именно U9-связь с действиями, использовать крупные видимые пороги
с лимитом и альтернативной ценой; сами пороги ещё не согласованы.

Начать с линейных прибавок для непрерывных величин, отдельных порогов для целых
действий, ограниченного числа множителей. Без итоговых коэффициентов до эталонных
сценариев: время убийства, ходы до пробоя брони, удержание позиции, число доступных
действий. Не допустить двойного бонуса: повышение Силы через StatsBag уже должно
учитываться один раз, а не повторно как «модификатор от предмета» в уроне.

## 4. Броня — дизайн D0 и первый реализованный срез D2

U, 2026-09-21: оставшиеся решения по броне принимает ведущий, обращаясь только
при противоречиях. A: D0 закрыт; принятые правила и решения ведущего, полные числа,
карта нынешних HP-путей и будущие границы D1/D2 — [ARMOR_DAMAGE_D0](ARMOR_DAMAGE_D0.md).
Q1–Q6 повторно не обсуждать. Последующим «продолжай» поручен и реализован первый [срез D2](ARMOR_DAMAGE_D2.md).
Отдельно выполнен [D1](ATTACK_DAMAGE_D1.md): выделен нынешний расчёт без изменения поведения.

Принято пользователем:

- До всего попадания при Amax>0 p=clamp(1-2*Acurr/Amax,0,1). При Amax=0:
  p=0 с временным запасом, иначе p=1. Компоненты одного hit не пересчитывают p.
- Одинаковые тип/политика объединяются до округления; дроби сохраняются через
  модификаторы, затем один floor → D. H0=floor(D*p), B0=D-H0; floor по защищённым ветвям.
- Для каждого типа rA — броня, rH — естественная защита. R_B=min(rA+rH,L_B),
  R_H=min(rH,L_H); естественная защита один раз. Остаток брони проходит в HP без
  повторной защиты. D=200, A=50/100, rA=20%, rH=30% → 50 A/50 HP.
- Лимит каждой ветви по умолчанию 75%; повышается только перками, без абсолютного
  потолка. У сопротивлений нет нижней границы. При R>100% обе ветви лечат HP,
  не броню: floor положительного лечения, без minimum-1; 10 при 110% → +1 HP.
- Весь HP-урон/лечение hit дают одну запись clamp(HP_before-T_damage+T_heal,0,HPmax).
  Смерть по итогу, без промежуточной смерти или раннего overkill/HPmax-clamp.
  Состояние допускает нужная положительная HP-часть до лечения, с учётом иммунитета/источника.
  Физический урон и компенсирующее огненное лечение могут оставить HP прежним и дать кровотечение.
- При нехватке брони расход между типами пропорционален их повреждающим ветвям после защит:
  floor, крупнейшие остатки, стабильный порядок типов. Это отдельное правило от расхода по вещам.
- Отдельной прочности нет. Amax=sum(A_i) надетого комплекта; a_i — остаток конкретной вещи.
  Расход не уменьшает max; снятие/замена только вне боя сохраняют остаток экземпляра.
  Все свойства надетой вещи работают при a_i=0, кроме явно зависящих от остатка условий.
  Сопротивления вещей складываются в rA по типу и не переходят в прямую HP-ветвь.
- Обычный расход случайный: один предмет принимает сколько может, остаток — следующий;
  среди a_i>0 веса равны A_i, а не остатку. Временная броня тратится перед вещами.
- После боя обычная броня сама не восстанавливается. Заклинания работают и в бою:
  восстановление пропорционально недостаче, floor/крупнейшие остатки/стабильный порядок вещей.
  Излишек — общий запас персонажа E, Acurr=sum(a_i)+E, без увеличения Amax.
- В бою можно создавать E при полном обычном запасе и Amax=0; повторные применения
  складываются с оставшимся E без предела. E исчезает после боя, если перк не задаёт другое.
  Создание нового E вне боя пока отложено.
- Между уровнями ремонт на экране персонажей требует общего ресурса отряда;
  расход пропорционален фактически восстановленной обычной броне (последний U 2026-09-21).
- Стойка уменьшает прямой удар ×0.7 до разделения, бережёт A и HP. Равновесие работает
  без HP-урона. Collision/fall — отдельные попадания через броню; пропасть — прямая смерть.

Решения A, принятые ведущим в рамках поручения (точный контракт — §9 ARMOR_DAMAGE_D0):

- Фиксировать защиты/модификаторы до всего hit; серия/AoE/последствия имеют отдельные hit ID.
  Первые типы physical/fire, стабильный реестр; обходы защиты только явной политикой эффекта.
- Перки складывают прибавки лимита в процентных пунктах по типу/ветви; одинаковый effect ID
  не дублируется. +15 и +20 к базовым 75 дают 110%. Названия и ранги — контент, не блокер D0.
- Стабильная идентичность предмета отделена от текущего владельца. RNG — injected combat stream,
  один draw при выборе среди нескольких, ноль при отсутствии выбора; preview использует клон.
  E хранится по источникам/срокам, сначала тратятся ближайшие к истечению записи.
- Успешный каст оплачивается полностью; V=0 — отказ без оплаты. Вне боя при M=0 — отказ,
  иначе восстановление ограничено недостачей, излишек не сохраняется. В бою излишек становится E.
- Рабочий ресурс — ремонтные материалы; начальный курс 1 материал за 1 обычной брони.
  Игрок выбирает вещь/набор вещей персонажа и бюджет; частичный ремонт распределяется по недостаче,
  списывается только фактическое восстановление. Реализация экрана/добычи ресурса относится к D4.
- Отдельный результат hit хранит повреждающие части, лечение, расход брони и net HP.
  damaged/healed сохраняют фактический смысл; старое лечение «при HP-уроне» не срабатывает
  от armor-only/net-zero. Команды состояний используют нужную часть hit до лечения.
- Базы/пороги последствий, цена/срок стойки и impact ×0.5 сохраняются; collision/fall физические,
  без повторного множителя стойки. Нынешние lethal-клетки, как пропасть, дают прямую смерть.

D0 закрывает дизайн брони, но не каталог всех состояний, перков/заклинаний или весь хаб.
Ведущий выбирает конкретный контент и точные API в порученном срезе; пользователь нужен
при противоречии с принятыми правилами. D1/M2a выполнен отдельным поручением;
D2 и срез D3 реализованы в пределах своих контрактов; D4–D5/M1/M2b/M3–M4 не запущены.

## 5. Расширяемый боевой расчёт — предложение P, не существующий API

«Динамический» должен означать сборку из данных и проверенных обработчиков.
Фазы и порядок всё равно обязаны быть определены, иначе результат зависит от
порядка надевания вещей, обхода коллекции или вызова UI.

Рекомендуемые границы:
1. Определения собирают типизированные компоненты урона и происхождение каждого.
   Источник воздействия, автор, владелец предмета и цель — разные роли;
   огонь окружения не требует фиктивного атакующего.
2. Чистый расчёт принимает фиксированные входы, выполняет согласованные стадии
   бонусов/множителей/маршрутизации/защиты и возвращает объяснимый результат.
   Impact и база столкновений/падения остаются отдельными каналами.
3. Команда повторно проверяет допуск и применяет результат через существующую
   очередь: ресурсы, смерть, последствия, реакции. Расчёт сам не меняет мир.
4. UI читает объяснение и результат настоящего forecast; BT выбирает намерение.
   Ни UI, ни BT не реализуют собственную формулу брони.

Группировка по источнику нужна для объяснения, снятия и владения. Порядок арифметики
задают операция/фаза/приоритет/стабильный ID, а не категория «артефакт/перк».
Не обещать, что любая новая механика будет только данными: новая операция требует
обработчика, валидации, копирования/codec, тестов и поддержки прогноза.
Первое доказательство расширяемости — два типа урона и второй вариант известного
модификатора без специальных ветвей в board/flow/UI. DSL/ECS и скрипты из snapshot
для этого не нужны. Точное API выбирает Астра после адресного чтения кода.

Нынешний ARMOR нельзя молча переименовать в текущий запас брони: меняется смысл
сериализованных данных. Новые значения/max/current, версия снимка, чтение старых
форм и политика миграции получают отдельный контракт. Не удалять старые enum IDs.
Любая новая влияющая подсистема входит в snapshot/restore/forecast целиком;
неподдерживаемый эффект отклоняется явно, а не исчезает из прогноза.

## 6. Трупы, клетки и цикл забега — предложение P

Труп — отдельная запись со стабильным ID, клеткой, исходным unit ID при наличии,
типом существа и принадлежностью на момент смерти. На клетке хранить коллекцию/индекс,
количество выводить из неё; два независимых изменяемых счётчика создают рассинхрон.
Смерть создаёт запись один раз через общую цепь последствий. Труп не занимает
живую occupancy автоматически. Отдельно решить пропасть, исчезающие призывы,
сжигание/поглощение и восстановление. Мёртвый UnitState сейчас не готовая модель трупа.

Клетку разделить на геометрию/проходимость, поверхность, наложенные эффекты,
лежащие объекты/трупы. Не создавать enum для каждой комбинации «трава+огонь+дым».
Правило взаимодействия получает событие и порождает команды; новая комбинация
известных правил — данные. Нужны единое время эффектов, стабильный порядок,
границы распространения и лимиты цепей. Выбор персонажа не тикает эффекты.
Дым требует явной политики линии выстрела, отдельно от стоимости движения.

Первый цикл хаба: выбор небольшой команды → экипировка → одна-две авторские
карты → возвращение вещей и показ результата → повторный выход. До его кода
определить минимальные переходы и восстановление ресурсов. Постоянный инвентарь,
переносимые вещи отряда и временные данные боя имеют явное владение/идентичность:
предмет при выдаче перемещается или резервируется, а не бесконтрольно копируется.
Возврат после поражения/загрузки не дублирует вещь и не пополняет её по ошибке.
Полный крафт, генератор, множество классов и графика не нужны для этого доказательства.
