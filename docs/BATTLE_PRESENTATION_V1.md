# Первый образец отображения боя — V1

Статус: предложение границ первого образца, не реализованный API.
Порядок работы и пожелания пользователя принадлежат DESIGN_DIRECTION §7:
предварительно пиксель-арт, конкретный стиль пользователь подберёт позже.
Основание: `d5faf3a1d4fb42f81992a4e536963288942b3c31`, 2026-09-30.

## Наблюдаемый результат

Один бой на временных фигурах должен показывать, кто действует, где происходит
попадание и какие последствия вызваны. Движение идёт по исполненному пути;
удар, изменение HP/брони, реакция, толчок, падение и смерть читаются в порядке
реальных событий. Действия противника показываются последовательно.
Изменение состояния обозначается у затронутой фигуры; журнал сохраняется
как дополнительное объяснение. Точные намерения врага заранее не раскрываются.

P состава первого образца: существующее изометрическое поле и текущие фигуры,
движение, обычный удар/выстрел, внешний маг K18, реакции/пространственные
последствия, HP/броня/статусы и исход. Временная отрисовка показывает событие;
полноценные покадровые движения персонажей создаются вместе с их будущим артом.
Камера, интерфейс хаба/карты, состав механик и баланс не входят в этот пакет.

## Что подтверждено в текущем коде

- `BattleDemoIsoVisual` рисует геометрию и значения `BattleUnitView`;
  текущая изометрическая сетка задаётся `IsoGridConfig`, исходный тайл 128×64.
  Это размеры нынешней проекции, не принятый размер будущего пиксельного ассета.
- `BattleDemoBoard` хранит проекцию показанного поля и уже имеет частное
  отображение падения. Универсальной последовательности всех действий нет.
- `BattleDemo` принимает результат worker и выводит `ActionReceipt`;
  граница владения и синхронный fallback — [BATTLE_EXECUTION_UI](BATTLE_EXECUTION_UI.md).

## Архитектурные условия для реализации

Использовать штатные средства Godot: [Tween](https://docs.godotengine.org/en/stable/classes/class_tween.html)
для параметров движения/вспышек, [AnimationPlayer](https://docs.godotengine.org/en/stable/classes/class_animationplayer.html)
для подготовленных последовательностей, [AnimatedSprite2D](https://docs.godotengine.org/en/stable/classes/class_animatedsprite2d.html)
для будущих покадровых спрайтов. Выбирать нужный инструмент по конкретному эффекту;
собственный проигрыватель ключевых кадров или универсальный движок анимаций не нужен.
Уже имеющееся падение использует `create_tween()` в `BattleDemoBoard.animate_fall`.
Новая работа — подключение игровых событий, порядка показа, HUD и сменяемых визуалов
к этим средствам; это не создание встроенных возможностей Godot заново.

P: отдельный слой представления использует копии показанного состояния и
завершённых событий. Он не вызывает повторное исполнение команды, не бросает RNG
и не меняет позиции/HP/ресурсы боевого runtime. UI не читает session во время
исключительного владения worker. Визуальные узлы не получают live UnitState.

До реализации проверить достаточность существующих событий/receipt для каждого
показываемого перехода. Недостающую информацию нельзя выдумывать по финальному
положению фигур: нужны явные значения на разрешённой границе публикации.
Обновление HUD/фигур согласовать с проигрываемой последовательностью, чтобы
смерть или потеря HP не показывались раньше своего попадания.

P управления: до завершения последовательности следующее игровое действие/шаг ИИ
ожидает; ускорение или пропуск меняют только представление. Пропуск заканчивается
на том же опубликованном состоянии. Reset/выход отбрасывают старое отображение
с соблюдением существующего join. FAULTED показывает только исполненный prefix.

## Проверка готовности образца

Один воспроизводимый бой на текущем ядре: движение → удар → фактические
последствия → следующий действующий. Отдельно проверить пропуск/ускорение,
выход во время показа, смертельный исход и каскад реакции/толчка/падения.
Сравнить конечные snapshots, события, RNG и ресурсы с тем же боем без показа;
прогноз остаётся изолированным, hover не запускает боевые анимации.
Тесты представления и независимое ревью — после записи кода по AGENTS.
Это не повторная ручная приёмка каждой механики ядра.

Стиль, палитра, персонажи, размеры/направления спрайтов и схема их анимации
остаются открыты. Не выпускать финальные ассеты и не закреплять их формат
до выбора пользователя; временный образец должен позволять заменить отрисовку.
